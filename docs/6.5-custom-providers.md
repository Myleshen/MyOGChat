# 6.5 — Custom upstream providers

Status: **implemented and unit-tested; not deployed.**
**Guiding principle: simple, fast, snappy, minimal resources.**

A signed-in user can add their own OpenAI-compatible endpoint — NVIDIA NIM
(`build.nvidia.com`), OpenRouter, a local vLLM/Ollama gateway, anything that
speaks `POST <base>/chat/completions`. Its models then appear in the model picker
next to the built-in OpenCode catalog, and chats run on the user's own key
against that host.

## What it supports

| | |
|---|---|
| Dialect | `chat` only (`/chat/completions`, streaming SSE, `tool_calls`) |
| Model list | fetched from `GET <base_url>/models` at add time, on refresh, and when an edit changes the URL or key |
| Selection | model id `"<slug>/<vendor-id>"` (e.g. `nvidia-nim/meta/llama-3.1-8b`) |
| Key | one per provider, encrypted at rest and never returned |
| Prices | unknown → `cost_tracked:false`; tokens are still recorded |
| Tools | the normal tool loop works through a custom provider |
| Vision / OCR | **not** offered for custom models (chat-only, no vision flag) |
| Internal helpers | auto-title, project memory, image-prompt enhance and OCR vision stay on bare OpenCode ids |

The endpoint must be **absolute** `http`/`https` with no query, fragment or
embedded credentials. The model-list fetch is not a key check: some providers
(NVIDIA among them) answer `GET <base>/models` without a key, so a stored key is
only proven by the first chat message.

## Headers sent — and not sent

To the custom host, every streaming request carries:

```
POST <base_url>/chat/completions
Authorization: Bearer <provider key>
Content-Type: application/json
Accept: text/event-stream
User-Agent: myogchat/1.0
```

`x-opencode-session` is **never** sent to a custom host: that header belongs to
OpenCode. It is still sent on every OpenCode request, unchanged. The model-list
fetch sends the same Bearer key and User-Agent.

The wire model id is the **vendor id alone** (`meta/llama-3.1-8b`), not the local
`<slug>/…` selector. NVIDIA model ids contain a slash, so only the first slash
splits the two.

## Unresponsive models

A provider's model list is not a promise that every model serves. NVIDIA, for
example, lists 33 models but only 11 answer; for the rest it accepts the TCP
connection and then sends no header and no byte. A custom-provider call
therefore has a **first-byte timeout of 60 s**: if nothing arrives in that time
the turn fails with

```
provider did not respond within 60s (model "<vendor id>"); the model may not be available — try another model
```

The timeout covers only the wait for the first byte. Once it arrives the
watchdog is stopped and the reply may stream for as long as `streamTimeout`
(5 minutes), so long answers are never truncated. OpenCode turns are unaffected
(no watchdog). If you see this message, pick another model from the same
provider: the endpoint and key are fine.

## Costs

Third-party prices are unknown, so the app does not invent one. Custom replies
report `cost_tracked:false` and `cost_micros:0`. Prompt/completion/cached tokens
are still counted in usage and quotas. The SPA shows "not tracked" for these
entries once its cost display is wired to `cost_tracked`; this change ships the
API field, not the UI.

> The provider panel lives in Settings → AI & access → Providers; the API calls
> below are the same thing from a terminal.

## Editing a provider

Every row in the Providers panel has **Edit** next to *Refresh models* and
*Delete*. It reopens the add form filled in — name and base URL prefilled, API
key blank with "Leave blank to keep the current key" — and saves only the fields
you changed. The blank key is omitted from the request entirely.

`PATCH /api/me/providers/{id}` accepts any of `name`, `base_url`, `api_key`, all
optional; a body with none of them is a `400`. An empty string is never valid for
any of the three: "unchanged" is expressed by **omitting** the field, never by
sending `""`.

- **Name only** — 1..64 runes, stored without contacting the provider.
- **New base URL and/or key** — re-fetched exactly as on add (`GET
  <base_url>/models`, `Authorization: Bearer <key>`, `User-Agent:
  myogchat/1.0`, 10 s). Success stores the new endpoint, key and fresh model
  list together; failure returns `400 {"error":"could not list models: …"}` with
  the upstream message and **changes nothing** — not even a name sent in the
  same request.

### The slug never changes

A provider's slug (`nvidia-nim`) is fixed for life. Local model ids are
`"<slug>/<vendor-id>"` and a conversation stores the model id it was created
with, so a slug that followed the name would orphan every chat pinned to the old
one. Renaming a provider to "NVIDIA NIM 2" therefore leaves
`nvidia-nim/meta/llama-3.1-8b` — and every conversation using it — untouched.
New providers still get a unique slug (`-2`, `-3`, … on collision).

### What a URL change does to existing conversations

Nothing breaks and nothing is rewritten. A chat pinned to
`nvidia-nim/meta/llama-3.1-8b` keeps that id; its next message goes to the **new**
base URL with the (possibly new) key, and the old host is never contacted again.
If the new endpoint does not serve that vendor model, the provider's own error
surfaces on the next message — the model list shown after the edit is the early
warning. A key change is re-validated at edit time by the same model-list fetch.

## NVIDIA example

1. Create a key at <https://build.nvidia.com> (free tier is enough).
2. Add the provider:

   ```sh
   curl -sS -b cookies.txt -X POST https://chat.example.com/api/me/providers \
     -H 'Content-Type: application/json' \
     -d '{"name":"NVIDIA NIM",
          "base_url":"https://integrate.api.nvidia.com/v1",
          "api_key":"nvapi-…"}'
   ```

3. The server calls `GET https://integrate.api.nvidia.com/v1/models`; on success
   the provider is created with its models (for example
   `nvidia-nim/meta/llama-3.1-8b`) and they appear in `GET /api/models`.
4. Start a chat with that model id:

   ```sh
   curl -sS -b cookies.txt -X POST https://chat.example.com/api/conversations \
     -H 'Content-Type: application/json' \
     -d '{"model":"nvidia-nim/meta/llama-3.1-8b"}'
   ```

5. **Refresh models** (`POST /api/me/providers/{id}/models`) re-fetches the list
   when NVIDIA adds or retires one.

A base URL without the `/v1` suffix will not work for NVIDIA, because the server
appends only `/models` and `/chat/completions`.

## Security notes

- The key is encrypted per user with AES-256-GCM (`internal/secret`, key = the DB
  `encryption_key`) and is **never** returned by any endpoint — only `has_key`.
- Provider rows are owner-scoped: another user's id behaves as `404`, and their
  provider never appears in your model list or is usable in a chat.
- Deleting the provider deletes its key with the row.
- A custom base URL is a user-supplied outbound URL. That is the same trust level
  as the per-user Linkwarden and calendar URLs: any signed-in user can point the
  server at a host they control. There is no allowlist.
