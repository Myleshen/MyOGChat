# 5.10 — Reuse the empty draft chat

Status: researched, **planned** (not implemented). Design of record.

## Problem

Every "New chat" persists a fresh `title=""` row, so the sidebar fills with
"Untitled" chats. If an empty (zero-message) untitled draft already exists, it
should be reused instead.

## Current behaviour

- `createConversation()` (`static/app.js`) POSTs immediately and prepends the row.
- The sidebar "New chat" handler only reuses the **currently open** blank draft.
  Navigate away / reload and you get another duplicate.
- The server always creates a fresh UUID; there is no draft notion. "Empty" is
  only `HasUserMessage` (user-role), used by regenerate.

## Design — server-side find-or-create

A **reusable draft** is a conversation owned by the caller where:
`title == ""` **and** it has **zero rows in `messages`** (not merely no *user*
message — a failed send can leave a user row with no title) **and** `project_id`
matches the request scope (NULL-safe) **and** `pinned == 0`; pick the most
recently updated.

- **Store:** `FindReusableDraft(ctx, userID, projectID) (Conversation, error)`
  (`ErrNotFound` when none):
  `WHERE user_id=? AND title='' AND pinned=0 AND project_id IS ? AND NOT EXISTS
  (SELECT 1 FROM messages m WHERE m.conversation_id=c.id) ORDER BY updated_at DESC LIMIT 1`.
- **Server:** `handleCreateConversation` accepts `reuse_empty:true`; on a hit it
  returns `200` with the existing draft (optionally aligning model/effort to the
  request when the caller explicitly picked a different model), else falls
  through to the existing `201` create. Non-`reuse_empty` stays `201` (back-compat).
- **SPA:** `buildNewChatBody()` sends `reuse_empty:true`; `createConversation()`
  dedupes `state.conversations` before `unshift` (otherwise a reused id is
  duplicated). The existing open-draft fast path stays. `ensureConversation`
  inherits reuse via `createConversation`.

**Why server-side:** only the server knows ownership and "zero messages" (the
list JSON has no count), it fixes reload/tabs, and every new-chat path already
funnels through `POST /api/conversations`.

## Decisions to confirm

1. Exclude pinned drafts from reuse? (recommended: yes, so pinning is never fought)
2. On reuse with a different model picked: align the draft's model/effort to the
   request, or keep the draft's and snap the picker back? (recommended: align)
3. Multi-tab simultaneous POST race: accept (recommended for v1) or add a
   client `draft_key` (needs a migration — later).
