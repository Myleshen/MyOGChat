# 6.2 — Rolling project memory

Status: **shipped in v0.2.0**, running on the Pi. Verified live: memory was
written ~6 s after a reply, and a brand-new chat in the project answered from
injected memory with zero tool calls.

## Problem

A project's `instructions` are written by hand and stay fixed. Facts learned
while chatting in the project — the stack someone uses, a naming decision, an
open task — are forgotten by the next chat unless they are pasted in again.

## What it is

Each project has a `memory` text. After every **successful** assistant reply in
a chat filed in that project (and only when `memory_auto` is on), a cheap
background call merges that turn into the memory. The memory is then injected
into every later chat of the project, so the project learns as it is used.

Two additive columns, migrated in `internal/store.migrate()`:

| column | type | default | meaning |
|---|---|---|---|
| `memory` | TEXT | `''` | the rolling project memory |
| `memory_auto` | INTEGER | `1` | whether replies update it automatically |

Both are per project and owner-scoped; no project is visible or writable across
users.

## Injection

`projectInstructions` is the single place that builds a chat's system prompt. It
returns the project's `instructions` and, when memory is non-empty, appends a
block separated by a blank line:

```text
<project instructions>

## Project memory
<memory text>
```

Both upstream dialects (chat-completions and responses) receive that exact
string — chat as the leading system message, responses as the `instructions`
field — so there is one composition point, not two.

`maxInstructionsRunes` (8000) applies to user-authored instructions only; memory
has its own 32000-rune cap so the combined prompt stays bounded.

**32000 is a deliberate ceiling, a context/attention trade-off — not a limit of
the model.** Memory is re-sent on every turn of every chat in the project, so at
the ceiling it adds roughly **8k tokens of extra input on every turn** in that
project: about **$0.0012/turn on the cheapest model, cached after the first
turn**. Keep it tighter in practice; the model is told to compress older detail
first rather than drop structure. Past this size the right move is a separate
project or `read_chat`, not a bigger memory.

## The rolling update

After the assistant message is stored (never before, never on a failed reply),
`runReply` starts a goroutine exactly like the auto-title job:

- one non-streaming call to `mimo-v2.6-flash`, `max_tokens` 4000, 30 s timeout;
- on the caller's already-resolved per-request API key, with the conversation
  UUID as the upstream session;
- prompt = current memory + this turn's user message (≤2 KB) and the reply
  (≤6 KB) + the rules to keep only durable facts, compress older detail first
  rather than drop structure, and return the updated memory alone, under 32000
  characters;
- result trimmed to 32000 runes, UTF-8-safe. An empty result leaves memory
  unchanged.

Nothing waits on it: the reply's `done` frame is sent without the memory call.
A failure is logged and dropped — the reply is never affected.

## Cost per turn

Two cost lines, both billed to the user's own key:

- the merge call — one extra short completion per successful project-chat turn
  (`max_tokens` 4000 on the cheapest model, a fraction of a cent);
- the injection — the memory is part of the system prompt on **every** turn of
  every chat in the project, so a 32000-character memory adds roughly **8k
  tokens of input per turn** (about **$0.0012/turn** on the cheapest model,
  cached after the first turn). The cap is a deliberate context/attention
  trade-off for that reason.

Title generation already adds one call on a chat's first turn. Turn memory off
per project with `memory_auto: false`; unfiled chats and failed/stopped replies
cost nothing.

## Safety: compare-and-set

The update never blindly overwrites. It reads the memory, asks the model, then
writes:

```sql
UPDATE projects SET memory = ? WHERE id = ? AND user_id = ? AND memory = ?
```

using the value it read. If the user edited the memory (or toggled it) while the
call was in flight, the `WHERE memory = ?` clause matches nothing, the write is
dropped at **debug** level, and there is no retry. The user's text always wins.

## Clearing it

- `PATCH /api/projects/{id}` with `{"memory": ""}` empties it;
- turn automatic updates off with `{"memory_auto": false}` while keeping the
  existing text.

A project can be fully reset by clearing the memory and leaving auto-updates on.
Deleting the project deletes the memory with it.
