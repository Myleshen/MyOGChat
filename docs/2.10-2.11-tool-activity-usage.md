# 2.10 Persist tool activity + 2.11 Usage & quota accounting

Both features land in one worktree/branch (`feat/tool-activity-usage`). 2.10 is
a small, prerequisite-friendly subset; 2.11 reuses the same schema/migrate
surface. Contract: `API_CONTRACT.md` §8.4 (message JSON) and §11 (usage).

## 2.10 — Persist tool activity

### Problem
The inline tool block (`web_search · done · …`) was rendered live from SSE
`event: tool` frames but never stored, so it vanished on reload / re-render.

### Data model
`messages` gains an additive `tools TEXT` column (JSON array
`{name,status,summary}`), mirroring `messages.attachments` (2.3). It is added in
`internal/store.migrate()`, not the base DDL.

### Store (`internal/store/store.go`)
- `ToolActivity` type; `Message.Tools []ToolActivity` (`json:"tools,omitempty"`).
- `messageCols` / `scanMessage` / `InsertMessage` updated (placeholders 14→15).
  Malformed JSON is dropped on read (same contract as `attachments`); a message
  with no tools round-trips as `nil`.

### Server (`internal/server/chat.go`)
- `streamReply` collects `upstream.EventTool` into `[]store.ToolActivity` via
  `mergeToolEvent`, which mirrors the SPA's `updateToolActivity`: a `running`
  event opens an entry; a terminal (`done`/`error`) event closes the most recent
  matching running entry, else appends.
- The collected slice is set on the assistant message before `InsertMessage`.
- Error/abort paths return before the assistant row is saved, so their tool
  activity is not persisted (consistent with the message itself not being
  saved). `regenerate` deletes the trailing assistant row and re-collects, so no
  stale tools remain. Tools run sequentially (`upstream/agent.go`), so there is
  never true concurrency to reconcile.

### API / UI
`GET /api/conversations/{id}` already marshals `[]store.Message`, so the new
JSON field flows through with **no handler change**. The SPA already renders
`m.tools` via `buildToolsBlock`; the optimistic `ui.tools` and the server-side
merged list are byte-identical, so `refreshCurrentConversation()` converges with
no flicker. Only the stale comment in `static/app.js` was corrected and the
`static/sw.js` cache version bumped (`v8` → `v9`).

## 2.11 — Usage & quota accounting

### Data model (no new table)
Usage is an aggregate over assistant `messages` joined to `conversations` for
owner scoping:

```sql
SELECT … FROM messages m JOIN conversations c ON c.id = m.conversation_id
WHERE c.user_id = ? AND m.role = 'assistant' AND (? = 0 OR m.created_at >= ?)
```

`created_at` is unix **millis**; days bucket with
`strftime('%Y-%m-%d', m.created_at/1000, 'unixepoch')`. Cutoff `0` = all time.
An additive index `idx_messages_created` (in `migrate()`'s index loop) supports
range scans.

### Store (`internal/store/store.go`)
- Types: `UsageTotals`, `UsageRow` (by-day / by-model bucket), `UserUsage`
  (admin view).
- `UserUsageTotals(ctx, userID, cutoff)`, `UserUsageByDay`,
  `UserUsageByModel`, `AllUsersUsage(ctx, cutoff)`.
- Per-user overrides: `users.daily_token_limit` / `users.monthly_cost_limit`
  (INTEGER, NULL = inherit), added to `userCols`/`scanUser`/`InsertUser`, plus
  `SetUserLimits(ctx, id, daily, monthly, now)`.

### API (`internal/server/usage.go`)
- `GET /api/me/usage?range=7d|30d|all` (any user) → totals + `by_day` +
  `by_model` + a `quota` status block. `range` defaults to `30d`.
- `GET /api/users/usage?range=…` (admin) → `{"range","users":[…]}` (aggregates
  only; admins never read others' chats).
- `usageCutoff` maps the range to a start-of-UTC-day cutoff (0 = all).
- `usageSettings` is merged into `GET /api/settings`; `PATCH /api/settings`
  accepts `daily_token_limit` / `monthly_cost_limit` (`>= 0`, decimal strings).
- `PATCH /api/users/{id}` accepts the overrides as **nullable numbers**
  (`nullableInt64`): omitted = unchanged, `null` = clear/inherit, number =
  override.

### Quotas
Global settings `daily_token_limit` (prompt+completion tokens per UTC day) and
`monthly_cost_limit` (`cost_micros` per UTC calendar month); `0` = off. Created
with defaults in `main.go` `run()`.

`checkQuota` is called in `handlePostMessage` and `handleRegenerate` **after
`resolveKey`, before the user message is persisted** (so a rejection stores no
orphan row). It returns `429` with a clear message on a hit, skips all queries
when both limits are `0`, and **fails open** on a DB error (logs a warning) so a
transient fault cannot lock users out. Free models (`cost_micros == 0`) never
trip the cost limit; the token limit still applies.

### UI (`static/index.html`, `static/app.js`, `static/style.css`)
A self-contained `#usage-section` (2.5/2.6 pattern) in the Settings page,
visible to everyone: range selector, totals, by-model lines, quota status.
Admins additionally see `#usage-admin` with the limit controls (daily tokens,
monthly USD) and an all-users table. Monthly cost is shown as
`cost_micros / 1e6`. `sw.js` cache bumped.

### Retention interaction
The janitor purges conversations older than `MYOGCHAT_RETENTION_DAYS` (default
30, max 60) by `updated_at`, cascading messages, so `all`/`30d` only cover
retained data. A **daily** quota is always exact (retention min 1 day); a
**monthly** quota is exact only when retention ≥ the current month (a shorter
window undercounts). Active conversations keep all messages regardless of age,
so a long chat can contribute older-than-retention usage — acceptable at
personal scale. Future option (out of scope): a `usage_daily` rollup written
before purge.

### Limitations
- Per-user override `0` means "inherit" (it cannot force "unlimited" while a
  global limit is set) — a documented limitation of the simple nullable-int
  scheme.
- Admin sees only aggregates (admins do not read others' chats, §9.5).
