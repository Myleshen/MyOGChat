# MyOGChat Phase 3 — Speech-to-Text (STT) & Text-to-Speech (TTS)

**Research report.** Scope: how to add voice to MyOGChat (single Go binary, `CGO_ENABLED=0`,
embedded vanilla-JS PWA, multi-user, running on a **Raspberry Pi 4B**) with an optional
**Proxmox GTX 1650 Ti Mobile (Turing, 4 GB)** LAN offload.

Date: 2026-10-10. All claims below are sourced (see §8). Where a number is an estimate from
an anchor benchmark rather than a direct measurement, it is labelled as such.

---

## 0. TL;DR

- **The Ollama assumption is wrong.** Ollama serves **LLMs and embedding models only**
  (backend = `llama.cpp`). It has **no `/v1/audio/transcriptions` or `/v1/audio/speech`
  endpoints**; audio input is an **open feature request** (`ollama#11798`). Speech needs a
  different runtime. Ollama is still perfect for **embeddings** — and can coexist in RAM with
  speech runtimes — but speech does not run "inside Ollama."
- **STT default: `whisper.cpp` with `base.en` (quantized) on the Pi 4B.** It runs ~1.5–2×
  *faster* than real time on the Pi's 4× Cortex-A72, at ~0.4 GB RAM, MIT-licensed, and ships a
  multi-arch (arm64) Docker image with an **OpenAI-like HTTP server**. `tiny.en` is ~3×
  realtime; `small.en` is *slower* than realtime (batch only).
- **TTS default: `Piper` on the Pi 4B.** Real-time on the Pi with `low`/`x_low` voices
  (sub-second per sentence), ONNX, ~0.1–0.3 GB. **License caveat:** the maintained repo
  (`OHF-Voice/piper1-gpl`) is **GPL-3.0** (it embeds espeak-ng); the old `rhasspy/piper` was
  MIT and is archived. For a *self-hosted, non-distributed* personal app this is fine.
- **GPU offload (optional):** the GTX 1650 Ti can run **faster-whisper `large-v3` (int8, ~3 GB)**
  or `distil-large-v3` (fp16) far below real time, plus **Kokoro** or Piper TTS, behind the same
  **OpenAI-compatible shim** pattern already planned for image generation. `large-v3` in **fp16
  does not fit** 4 GB; use int8.
- **Recommended build order:** (1) **TTS on the Pi (Piper)** — smallest, highest immediate value;
  (2) **STT on the Pi (whisper.cpp base.en)** — push-to-talk; (3) **optional GPU offload** on the
  Proxmox box for accuracy/latency.
- **Effort:** Pi-only STT+TTS MVP ≈ **4–6 days**; with GPU offload ≈ **8–12 days** total.
- **Architecture constraint:** the app must stay `CGO_ENABLED=0`. **Do not cgo-link**
  whisper.cpp/Piper. Run them as **separate HTTP services** (Docker container / systemd unit) and
  call them from Go — exactly like the existing OCR `DockerTesseract` seam, but **persistent**
  (model stays warm) rather than one-shot.

## 1. Correcting the Ollama assumption (verified)

**Claim to check:** *"Ollama can run STT/TTS side by side with the embeddings model."*

**Verdict: the speech half is false; the embeddings half is true.**

Primary evidence:

- **Ollama's supported backend is `llama.cpp` only** — "Supported backends: llama.cpp project
  founded by Georgi Gerganov" (Ollama README). `llama.cpp` runs text LLMs (and text+vision /
  some multimodal text models) and embedding models. It is not an audio runtime.
- **Ollama's own model library categories** are LLM / vision / **embedding** (e.g.
  `nomic-embed-text`, `mxbai-embed-large`, `qwen3-embedding`, `embeddinggemma`). There is **no
  STT or TTS category**.
- **Ollama's API surface** (`docs.ollama.com/api`) is `generate`, `chat`, `embed`/`embeddings`,
  `pull`, `push`, `create`, `show`, `list`, `ps`, `delete`, `copy`, plus OpenAI-compatible
  `/v1/chat/completions` and `/v1/embeddings`. **No audio endpoints.**
- **Audio input is an explicit open feature request**: *"Feature Request: Add Audio Input Support
  for Multimodal Models"* (`ollama/ollama#11798`) — "audio-capable models like Qwen2-Audio can be
  loaded but cannot receive actual audio input." So audio I/O is **not** a supported capability.
- The well-put summary from the audio-runtime space: *"Whisper.cpp only listens. Ollama and
  llama.cpp are text brains — they're not for audio. Kokoro and Piper only talk."*

**The nuance to be aware of:** a few people have packaged **LLM-based TTS** models as GGUFs and
hosted them on `ollama.com` (e.g. the community `legraphista/Orpheus` "TTS" model). That works
because Orpheus is fundamentally a **text LLM** that emits audio tokens — Ollama is still just
doing text generation; there is no audio pipeline, no proper WAV output, and no STT at all. It is
a curiosity, **not a supported STT/TTS path** and not what you want for MyOGChat.

**What to actually run:**

| Task | Runtime | Not Ollama |
|---|---|---|
| **Embeddings** (RAG) | **Ollama** (`nomic-embed-text`, `mxbai-embed-large`, …) ✅ | — |
| **STT** | `whisper.cpp`, `faster-whisper` (CTranslate2), `openai-whisper`, `Vosk`, hosted Whisper API | ❌ |
| **TTS** | `Piper`, `Kokoro`, `Coqui XTTS v2`, `espeak-ng`, hosted TTS API | ❌ |

Ollama **can** run **alongside** the speech runtimes (they're separate processes; RAM is the only
shared constraint — see §4), but it does not *serve* speech.

## 2. STT options

### 2.1 Comparison

| Engine | Model sizes | RAM (runtime) | Pi 4B speed (RTF) | GPU | Accuracy (EN WER) | License |
|---|---|---|---|---|---|---|
| **whisper.cpp** (GGML, C++) | tiny 75 MiB · base 142 MiB · small 466 MiB · medium 1.5 GiB · large 2.9 GiB | tiny ~273 MB · base ~388 MB · small ~852 MB · medium ~2.1 GB | **tiny ≈ 3× realtime; base ≈ 1.5–2× realtime; small ≈ 0.7× (slower)** | CUDA (Turing OK), Vulkan, Metal | tiny 7.6% · base 5.0% · small 3.4% · medium 2.9% | **MIT** |
| **faster-whisper** (CTranslate2) | same family, int8/fp16 CT2 | int8 ≈ 1.5 GB (small, CPU) | CPU: ~2× faster than openai-whisper; not the Pi's best choice | **CUDA 12 + cuDNN 9**, batched | same weights → same WER | **MIT** |
| **openai-whisper** (PyTorch) | same family | high | ~4× slower than faster-whisper; poor on Pi | CUDA | reference | **MIT** |
| **Vosk** (Kaldi) | small ~40–50 MB · large 1.4–1.8 GB | small ~300 MB | **Streaming, low-latency**, light | CPU only | small 9.85% (librispeech clean) · large 5.69% | **Apache-2.0** |
| **Hosted API** (OpenAI) | — | — | network-bound | — | `gpt-4o-transcribe` best | proprietary, per-use |

Notes and primary sources:

- **whisper.cpp** is a dependency-free C/C++ port of OpenAI Whisper with **integer
  quantization** and a built-in **HTTP server with an OpenAI-like API**
  (`whisper-server --host 0.0.0.0 -m /models/ggml-base.bin`). It ships **Docker images for
  `linux/arm64`** (`ghcr.io/ggml-org/whisper.cpp:main`, which bundles `ffmpeg`). It supports a
  **VAD** (Silero) mode that strips silence and speeds up transcription. Official memory table:
  tiny 273 MB, base 388 MB, small 852 MB, medium 2.1 GB, large 3.9 GB.
- **Pi 4B RTF** (4× Cortex-A72, `-t 4`, no GPU): the cleanest public measurement is MaibornWolff's
  Raspberry Pi 4 run — **tiny ≈ 2.85× faster than real time, base ≈ 1.88× faster, small ≈ 0.73×
  (i.e. slower than real time)**; "the runtime exceeds real time starting with the Small model."
  Other sources agree tiny/base are the real-time models on Pi 4 and small is batch-only. An
  academic Pi measurement reported RTF **0.23–0.41** for tiny, **0.61** for base, **1.88** for
  small. Practical implication: a 10-second push-to-talk clip with `base.en` transcribes in
  **~5–7 s**; `tiny.en` in **~3 s**.
- **Quantization** shrinks RAM and often speeds inference. whisper.cpp supports `q4_0/q5_0/q8_0`
  (and k-quants). `q5_1` is the common "production" choice; `q4_0` is often the best
  speed/size trade-off; `q2_k` hallucinates badly. Quantization on `base` keeps accuracy
  essentially unchanged in independent tests (~98% vs 98.4%).
- **faster-whisper** is up to **4× faster than openai-whisper** for the same accuracy via
  CTranslate2, with **8-bit quantization on CPU and GPU**, and a **batched** pipeline. GPU
  execution needs **cuBLAS for CUDA 12 + cuDNN 9** (satisfied on the Proxmox box — driver
  615.71.09 + CUDA already present). It does **not** need system ffmpeg (PyAV bundles it). It
  supports **distil-large-v3** and a **Silero VAD** filter. On the GTX 1650 Ti, **`large-v3` int8
  (~2.9 GB)** or **`distil-large-v3` fp16** fit 4 GB; `large-v3` **fp16 (~4.5–5 GB) does not**.
- **openai-whisper** is the reference PyTorch implementation — the slowest of the three; not
  recommended on a Pi.
- **Vosk** is the *streaming* option: per-language models ~50 MB, ~300 MB runtime, **zero-latency
  streaming API**, speaker ID, bindings for Go/Python/Java/etc., Apache-2.0. Lower accuracy than
  Whisper (9.85% WER small EN) but genuinely real-time and incremental on weak hardware.
- **Hosted API:** OpenAI Whisper/GPT-4o pricing (checked Aug 2026): `whisper-1` **$0.006/min**,
  `gpt-4o-transcribe` **$0.006/min**, `gpt-4o-mini-transcribe` **$0.003/min**, live/streaming
  `$0.017/min`. Accepts mp3/mp4/mpeg/mpga/m4a/wav/webm, **25 MB limit**. Useful only as a
  fallback; the whole point here is self-hosting.

### 2.2 STT recommendation

- **Default (on the Pi): `whisper.cpp` `base.en`, quantized (`q5_0`/`q4_0`), in a *persistent*
  `whisper-server` Docker container** (arm64 image; model stays resident). ~0.4 GB RAM, ~1.5–2×
  realtime, MIT. `tiny.en` if you want maximum speed, `small.en` only for batch/uploaded files.
- **Upgrade (on the Proxmox GPU): `faster-whisper` `large-v3` int8** (or `distil-large-v3` fp16)
  behind an OpenAI-compatible `/v1/audio/transcriptions` shim — highest accuracy, far below
  realtime.
- **Streaming alternative if you ever want live captions:** `Vosk` (Apache-2.0) is the pragmatic
  streaming engine; Whisper is fundamentally a chunk model.

## 3. TTS options

### 3.1 Comparison

| Engine | Quality | CPU/GPU need | Pi 4B feasibility | Latency | License |
|---|---|---|---|---|---|
| **Piper** (VITS/ONNX) | Good, natural | **CPU-only**, no GPU | ✅ **Real-time** (low/x_low voices; medium near-realtime) | sub-second/sentence; RTF < 1 | **GPL-3.0** (maintained `piper1-gpl`); old `rhasspy/piper` was **MIT** (archived) |
| **Kokoro-82M** (ONNX) | Very good (StyleTTS2 lineage) | CPU or GPU | ⚠️ **Slower than real time on Pi 4** (~80 MB int8); fine on Pi 5 / desktop / GPU | RTF ~1.4 (fp16) / ~4.5 (int8) on desktop CPU; **not real-time on Pi 4** | **Apache-2.0** (weights); `kokoro-onnx` MIT |
| **Coqui XTTS v2** | Excellent + **voice cloning** | **GPU-heavy** (~2 GB fp16) | ❌ not for Pi | realtime-ish on GPU | **CPML — non-commercial** (weights); code MPL-2.0 |
| **espeak-ng** | Robotic | trivial CPU | ✅ instant | ~0 | **GPL-3.0** |
| **Hosted API** (OpenAI TTS) | Very good, steerable | none | n/a | network-bound | proprietary, `$15/1M chars` (~$0.015/min) |

Notes and primary sources:

- **Piper** is a VITS model exported to ONNX, designed for embedded/CPU; it embeds espeak-ng for
  phonemization. It's **Home Assistant's default local TTS** (`en_US-lessac-medium`). It hits
  **real time on a Raspberry Pi 5 with no GPU** and the project explicitly targets Pi-class
  hardware; independent reviews say **Pi 4 works but is noticeably slower on `medium` voices —
  drop to `low`/`x_low` if latency matters**. It exposes a **lightweight HTTP server**
  (`python -m piper.http_server -m en_US-ryan-high`, i.e. `pip install "piper-tts[http]"`), plus
  CLI, Python, and C/C++ APIs. **License changed:** the original `rhasspy/piper` (MIT) was
  **archived read-only in Oct 2025**; active development is `OHF-Voice/piper1-gpl`, **GPL-3.0**
  (because espeak-ng is embedded). The maintainer says **Piper 2 is planned to move to Apache-2.0**.
  Individual **voice** files carry their own licenses (many CC0/CC-BY; some are non-commercial —
  check per voice).
- **Kokoro-82M** is an **Apache-2.0** 82 M-param model (54 voices, 8 languages, 24 kHz), ranked
  #1 on the TTS Spaces Arena for its size; ONNX weights ~80 MB (int8) / 169 MB (fp16). It runs
  **at/near real time on ordinary desktop CPUs** and is very fast on GPU, and community ports run
  it fully in-browser (WebGPU/WASM). **But on a Pi 4 (2 GB) it is slower than real time** — a
  hands-on Pi 4 report: *"on my Raspberry Pi 4 (2GB) the inference speed is less than real time,
  so these older TTS options [eSpeak/Piper] still have their place."* Use Kokoro on the Proxmox
  GPU or a Pi 5, not as the Pi 4 default.
- **Coqui XTTS v2** adds **zero-shot voice cloning** (6 s reference) and multilingual output, but
  needs a GPU (~2 GB fp16; OOM on a 6 GB RTX 3050 in one benchmark, so a 4 GB card is tight), and
  its **weights are licensed CPML — non-commercial only** (and Coqui shut down in Jan 2024, so no
  commercial license can be bought). For a personal app it's *legally* usable, but it's heavy and
  the project is unmaintained. **Not recommended.**
- **espeak-ng** is the robotic fallback — instant, tiny, GPL-3.0. Good as a last-resort default.
- **Hosted OpenAI TTS:** `tts-1`/`gpt-4o-mini-tts` ≈ **$15/1M chars (~$0.015/min)**, `tts-1-hd`
  $30/1M; 4096-char / ~2000-token request limits. Fallback only.

### 3.2 TTS recommendation

- **Default (on the Pi): `Piper`**, a `low`/`x_low` or `medium` English voice (e.g.
  `en_US-lessac-medium` for quality, a `low` voice for latency), served by
  `piper.http_server`. Real-time on the Pi, ~0.1–0.3 GB.
- **Upgrade (on the Proxmox GPU): `Kokoro`** (Apache-2.0, best quality-per-parameter) served via
  an OpenAI-compatible `/v1/audio/speech` shim. Piper-on-GPU is also fine if you want to reuse the
  same engine everywhere.
- **Zero-backend day-one fallback:** the browser's **Web Speech API** (`window.speechSynthesis`)
  gives free on-device TTS with no server work — good enough to ship the "read aloud" button
  immediately while Piper is wired up. (It is *not* self-hosted — the OS voice — so keep it as a
  fallback, not the default.)

## 4. Hardware reality

### 4.1 Raspberry Pi 4B (4× Cortex-A72 @ 1.5 GHz, 4–6 GB, **no GPU/NPU**)

| Task | Engine / model | Speed | RAM | Verdict |
|---|---|---|---|---|
| STT | whisper.cpp `tiny.en` | ~3× realtime | ~0.3 GB | ✅ comfortable |
| STT | whisper.cpp **`base.en`** | **~1.5–2× realtime** | **~0.4 GB** | ✅ **default** |
| STT | whisper.cpp `small.en` | ~0.7× (slower) | ~0.85 GB | ⚠️ batch/upload only |
| STT | Vosk small | streaming, real-time | ~0.3 GB | ✅ if you need live captions |
| TTS | **Piper** low/medium | **real-time (RTF < 1)** | ~0.1–0.3 GB | ✅ **default** |
| TTS | Kokoro int8 | slower than realtime | ~0.3 GB | ⚠️ Pi 5 / GPU instead |
| TTS | espeak-ng | instant | ~MB | ✅ fallback |

**The bottleneck is the CPU, not RAM.** Transcription with `base.en` pins all four A72 cores for
several seconds per utterance; while it runs, TTS/embeddings/chat are sluggish. Because usage is
**sequential** (speak → transcribe → chat → speak), this is fine for a personal app — but it is
**not** a "run everything simultaneously for several users" box.

**RAM budget check (4 GB Pi, all resident):** OS + Docker ≈ 0.5–0.8 GB · MyOGChat Go ≈ 4–50 MB ·
Ollama + `nomic-embed-text` ≈ 0.3 GB · whisper.cpp `base.en` ≈ 0.4 GB · Piper ≈ 0.1–0.3 GB →
**≈ 1.3–2.0 GB total.** So **STT + TTS + embeddings do fit side by side in 4 GB** — but you would
not want whisper `small`/`medium` resident at the same time. On a 2 GB Pi, drop to `tiny.en` +
a `low` Piper voice and/or offload.

### 4.2 Proxmox GTX 1650 Ti Mobile (Turing `sm_75`, 1024 CUDA cores, **4 GB GDDR6**, **no tensor cores**, **FP16 = 2× FP32**, driver 615.71.09)

| Task | Engine / model | Fits 4 GB? | Expected speed |
|---|---|---|---|
| STT | faster-whisper **`large-v3` int8** | ✅ ~2.9 GB | ≫ realtime (tens of ×) |
| STT | faster-whisper **`distil-large-v3` fp16** | ✅ ~2 GB | ≫ realtime, near-large accuracy |
| STT | faster-whisper `large-v3` **fp16** | ❌ ~4.5–5 GB | OOM/tight — **avoid** |
| STT | faster-whisper `medium`/`small` fp16 | ✅ | ≫ realtime |
| STT | whisper.cpp CUDA (`large-v3-turbo`) | ✅ (q5) | ≫ realtime |
| TTS | **Kokoro** | ✅ ~0.3–0.5 GB | first-audio tens of ms |
| TTS | **Piper** | ✅ ~0.3 GB | realtime, sub-100 ms first audio |
| TTS | XTTS v2 fp16 | ⚠️ ~2 GB (tight) | realtime-ish; **CPML non-commercial** |

FP16 runs at **2× FP32** on this Turing part (unlike Pascal), so pin **fp16** — but there are **no
bf16/fp8 tensor cores**, so never let a runtime pick bf16 (it silently falls back to fp32). CUDA
13 / PyTorch `cu128` fully support `sm_75` (the earlier Pascal-era "pin cu126" advice does **not**
apply). faster-whisper needs **cuBLAS (CUDA 12) + cuDNN 9** — already satisfied by the image-gen
setup on this box.

### 4.3 Self-host on the Pi vs LAN offload to Proxmox

| | Pi 4B (self-host) | Proxmox GTX 1650 Ti (LAN offload) |
|---|---|---|
| STT | whisper.cpp `base.en`, ~2× realtime, 5–7 s / 10 s clip | faster-whisper `large-v3` int8, ≫ realtime |
| TTS | Piper, real-time | Kokoro / Piper, near-instant |
| Privacy | everything on-device | audio/text crosses the LAN |
| Availability | no extra hardware; works if the Proxmox box is off | depends on the box being up; keep a Pi fallback |
| Complexity | low (one Docker service) | higher (LXC + driver + shim, same as image-gen) |
| Cost | electricity only | electricity only |

**Recommendation:** **default to self-hosted on the Pi** (Piper + whisper.cpp base.en) because it
is simple, private, and good enough for dictation and reading replies. **Offer the Proxmox GPU as
an optional upgrade** for (a) high-accuracy transcription of long recordings and (b) nicer voices —
reusing the **OpenAI-compatible shim** approach already chosen for image generation. Because the
client interface is OpenAI-compatible, the same Go code can later point at OpenAI's hosted audio
APIs with no change.

## 5. Integration design for MyOGChat

### 5.1 Hard architectural constraint

MyOGChat is **`CGO_ENABLED=0`** and ships as **one Go binary**. whisper.cpp and Piper are native
C++/Python — you **cannot** link them into the binary. Follow the **existing OCR pattern**
(`internal/ocr.DockerTesseract` shells out to a hardened Docker container) but with one crucial
change: **use a persistent service, not one-shot `docker run`.** OCR's Tesseract starts in
milliseconds; Whisper/Piper would **reload the model on every request** if invoked one-shot. Run
them as long-lived HTTP servers (model resident) and call them over `localhost`/LAN.

```
browser ──▶ Go (Pi) ──▶ [ speech service on the Pi  OR  OpenAI-compatible shim on the Proxmox GPU ]
 MediaRecorder / <audio>   internal/speech          whisper-server / piper.http_server
                                                    (or faster-whisper + Kokoro behind a shim)
```

### 5.2 New package: `internal/speech`

Mirror `internal/ocr`'s interface-plus-backend shape:

```go
package speech

// STT
type Transcriber interface {
    Transcribe(ctx context.Context, audio []byte, filename, mime string) (string, error)
}
// TTS
type Synthesizer interface {
    Synthesize(ctx context.Context, text, voice string) (audio []byte, mime string, err error)
}
```

Backends (all HTTP or subprocess — never cgo):

- `OpenAISTT` / `OpenAITTS` — speak the **OpenAI-compatible** wire shapes
  (`POST /v1/audio/transcriptions` multipart; `POST /v1/audio/speech` JSON) so the *same* client
  works against (a) a local `whisper-server`/shim, (b) the Proxmox shim, or (c) OpenAI hosted.
- `DockerWhisper` / `DockerPiper` — optional local fallbacks that exec a container (like
  `DockerTesseract`), for deployments that don't run the persistent services.
- `Disabled` (nil) — feature off; endpoints return `501`/`400` with a clear message, exactly like
  `ocrFunc` returning nil.

Config (env + DB settings, mirroring OCR §8.10):

| Var | Default | Notes |
|---|---|---|
| `MYOGCHAT_STT` | `auto` | `off` \| `local` \| `remote` \| `auto` |
| `MYOGCHAT_STT_URL` | `http://127.0.0.1:8080` | whisper-server or Proxmox shim base URL |
| `MYOGCHAT_STT_MODEL` | `base.en` | informational / passed through |
| `MYOGCHAT_STT_TIMEOUT` | `120s` | generous: Pi `base.en` ≈ 2× realtime |
| `MYOGCHAT_TTS` | `auto` | `off` \| `local` \| `remote` \| `auto` |
| `MYOGCHAT_TTS_URL` | `http://127.0.0.1:5000` | `piper.http_server` or shim |
| `MYOGCHAT_TTS_VOICE` | `en_US-lessac-medium` | default voice |
| `MYOGCHAT_TTS_TIMEOUT` | `30s` | |
| DB settings | — | `stt_enabled`, `tts_enabled` (admin), `tts_voice` (per-user) |

### 5.3 HTTP endpoints

Add to `internal/server/server.go` (per-user, session-authenticated):

```
POST /api/stt   multipart/form-data, field "audio" (+ optional "language")
                → 200 {"text":"…","duration_ms":N}
                limits: ≤ 25 MB and ≤ ~5 min; MIME sniffed
                → 400 on unsupported/empty; 503 if STT disabled

POST /api/tts   JSON {"text":"…","voice"?:"…","format"?:"wav"}
                → 200 audio/wav (raw bytes; Content-Type set) OR
                  200 {"audio_base64":"…","mime":"audio/wav","voice":"…"}
                cap input length (e.g. 4 000 chars, matching Piper/OpenAI limits)
                → 503 if TTS disabled

GET  /api/tts/voices   → [{id,name,lang,quality,installed}]   (optional)
```

Rationale for raw-bytes TTS: the SPA can play it with `new Audio(URL.createObjectURL(blob))` and
can cache per message; JSON+base64 is an alternative if you prefer uniform JSON.

Optional, high-value and low-cost: **treat audio like images in the attachment pipeline.**
`internal/extract` already delegates images to an injected `ocr.OCRFunc`. Add an analogous
`speech.STTFunc` so an uploaded **audio attachment** is transcribed into `attachments.text` — then
the model "sees" voice memos, and a `transcribe_audio` tool falls out for free (the model just
reads the attachment text). This reuses the whole 2.3/2.5 seam.

### 5.4 Audio formats

- **Browser capture (`MediaRecorder`):** Chrome/Android/Firefox produce
  **`audio/webm;codecs=opus`**; **Safari/iOS produce `audio/mp4` (AAC)**. The server must accept
  **both**. Detecting the codec server-side and converting is the robust path.
- **Whisper needs 16 kHz mono PCM WAV.** Two ways to satisfy this:
  1. **Server-side ffmpeg** (recommended): the whisper.cpp Docker image already **bundles ffmpeg**,
     and the `whisper-server` accepts common containers (webm/opus, mp4/aac, ogg, mp3, m4a, wav).
     Go uploads the raw blob; the service converts internally.
  2. **Client-side WAV**: encode WAV in the browser via Web Audio + AudioWorklet — avoids a server
     dependency but adds nontrivial JS and larger uploads.
- **TTS output:** Piper emits **16-bit PCM WAV** (`--output-raw` for streaming PCM). Serve
  `audio/wav` directly (the browser plays it natively); optionally transcode to **mp3/ogg** with
  ffmpeg to shrink payloads over the tunnel. Kokoro outputs 24 kHz WAV.
- **Caps:** reject > 25 MB; a 60 s Opus recording is ~0.5 MB, so the cap is generous.

### 5.5 Streaming & chunking

- **STT — v1 = push-to-talk (record → stop → upload → transcribe).** This is simplest, robust, and
  matches Whisper's chunked nature. **Skip live/partial transcripts in v1**: Whisper is not a
  streaming model, and rolling-buffer streaming (`whisper-stream`-style, re-transcribing every
  N seconds) is significant complexity for little personal-app value. If you later want live
  captions, add **Vosk** as a streaming engine behind the same `Transcriber` interface.
- **TTS — v1 = synthesize whole response, return one WAV.** Piper can stream raw PCM for lower
  first-audio latency (a nice v2). Kokoro/OpenAI expose streaming too. Not needed for v1.
- **VAD:** enable Silero VAD in whisper.cpp/faster-whisper to drop silence (faster, fewer
  hallucinations on trailing silence).

### 5.6 PWA UI (vanilla JS, no build step)

- **Mic button** in the composer:
  - `navigator.mediaDevices.getUserMedia({audio:true})` → `MediaRecorder` → collect chunks →
    on stop, `POST /api/stt` as `multipart/form-data`.
  - States: idle → recording (pulsing red, running timer) → transcribing (spinner) → insert text
    into the composer (append, don't clobber).
  - Handle: permission denied, no `MediaRecorder` (fallback: file input `accept="audio/*"`),
    `audio/mp4` on Safari. Stop tracks on completion.
  - Min 44px touch target, `safe-area` padding (mobile-first).
- **Speaker / play button on assistant messages:**
  - `POST /api/tts` with the message's plain text → `Audio(blob)`; toggle play/stop; show a spinner
    while synthesizing; cache the blob per message id.
  - Strip markdown/code fences before sending (Piper reads punctuation literally; code should be
    skipped or summarized).
- **Settings → new "Voice" section** (self-contained block, like `#ocr-section`):
  - "Speech to text" on/off (admin `stt_enabled`), status (available? which backend),
  - "Read replies aloud" default (browser-local), default voice (`tts_voice`),
  - backend status ("Pi local" / "Proxmox GPU" / "offline") from a health probe.
- **PWA/service-worker:** bump `sw.js` cache version; never cache `/api/*`.

### 5.7 Deploy / host provisioning

- **Pi (`deploy/speech-setup.sh`):**
  - `whisper-server` container (arm64): pull `ghcr.io/ggml-org/whisper.cpp:main`, download
    `ggml-base.en-q5_0.bin`, run `--host 0.0.0.0 -m … --convert` (ffmpeg bundled), restart-policy
    `unless-stopped`, resource-limited like the sandbox/OCR containers.
  - Piper: a small container running `python -m piper.http_server -m en_US-lessac-medium` (or a
    systemd unit); download the voice ONNX to a volume.
  - Both bound to `127.0.0.1` (never public); the Go service is the only caller.
- **Proxmox (optional, reuses the image-gen LXC/shim pattern):** run `faster-whisper` (via the
  `speaches` or `faster-whisper-server` OpenAI-compatible server) + Kokoro/Piper in the same LXC
  with the GPU passthrough; front with a bearer-token shim exposing
  `/v1/audio/transcriptions` + `/v1/audio/speech`. **LAN-only; never expose through the Cloudflare
  Tunnel** — the Pi reaches it over the LAN, exactly like the image shim.
- **Health probe:** `GET /system_stats`-style endpoint so Settings can show "online".

### 5.8 Timeouts, limits, failure modes

- STT timeout **120 s** (Pi `base.en` ≈ 2× realtime; a 60 s clip ≈ 30 s; cold model load adds
  seconds — the persistent server avoids this after the first request). TTS timeout **30 s**.
- Abort the upstream/speech call when the client disconnects (`r.Context()`), as the chat path does.
- Fail **open on the UI** (mic/play disabled with a clear message) and **closed on the API**
  (`503` when the feature is off/unavailable), matching the OCR `ocrFunc == nil` behavior.
- Never log audio or transcripts at info level (privacy); log durations/bytes only.

### 6.2 Recommendation (what to build, where, in what order)

1. **TTS first — Piper on the Pi.** Highest value for the least work: a "read replies aloud" button
   on every assistant message. Ship a **Web Speech API** fallback on day one so the button works
   before Piper is deployed. Wire the real `POST /api/tts` behind it.
2. **STT second — whisper.cpp `base.en` on the Pi.** A push-to-talk mic button. Accept
   webm/opus + mp4/aac, convert in the whisper container, return text into the composer. Keep it
   **push-to-talk**, not streaming.
3. **Optional: audio attachments → transcript** by extending the OCR/extract seam — gives
   `transcribe_audio` and voice-memo context with almost no new surface.
4. **Optional: GPU offload to the Proxmox GTX 1650 Ti** — faster-whisper `large-v3` int8 +
   Kokoro, behind an OpenAI-compatible shim, LAN-only, reusing the image-gen LXC pattern. Point
   `MYOGCHAT_STT_URL`/`MYOGCHAT_TTS_URL` at it; keep the Pi as fallback.
5. **Skip:** Coqui XTTS v2 (non-commercial weights, heavy, unmaintained) and live streaming STT
   (Whisper isn't a streaming model; add Vosk later only if needed).

**Bottom line:** self-host **whisper.cpp `base.en` (STT)** and **Piper (TTS)** on the Pi 4B as
persistent Docker HTTP services; keep the Go client **OpenAI-compatible** so the Proxmox GPU (or
OpenAI hosted) is a drop-in upgrade. **Ollama stays as the embeddings engine only — it cannot
serve speech.**

## 7. Open questions / risks

1. **Pi 4 thermal throttling** under sustained Whisper load (the Pi has no heatsink guarantee) —
   measure a long transcription and watch `/sys/class/thermal`.
2. **Piper GPL-3.0** — fine for self-hosted personal use; if MyOGChat binaries are ever
   *distributed*, keep Piper at arm's length as a **separate HTTP server** (as Pipecat explicitly
   recommends: use `PiperHttpTTSService` to keep it out of your app's license scope). Piper 2 is
   slated for Apache-2.0.
3. **Piper voice licenses** vary per voice (some non-commercial) — pick a CC0/CC-BY voice for the
   default.
4. **Safari/iOS `MediaRecorder`** yields `audio/mp4` — verify the whisper container converts it
   cleanly (some ffmpeg builds choke on Safari AAC).
5. **Cold-start latency** — a persistent whisper-server avoids model reload; make sure the deploy
   uses `restart: unless-stopped` and a health check so it's warm before first use.
6. **RAM on a 2 GB Pi** — `base.en` + Piper + Ollama may not all fit; use `tiny.en` + a `low`
   voice, or offload STT to the Proxmox box.
