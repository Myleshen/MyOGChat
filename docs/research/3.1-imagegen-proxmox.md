# Self-hosting image generation on a Proxmox GTX 1050 for MyOGChat

**Question:** can a 4 GB GTX 1050 in a Proxmox VE box run a local image model and expose
it to MyOGChat (Go + embedded SPA on a Pi 4B) — without paying for an external image API?

---

## 1. Verdict (TL;DR)

**GO — but only for SD 1.5 / SD 2.1 / SD-Turbo at 512×512.** The card is slow, not
unusable. Expect **~5–15 s/image** with a few-step model (SD-Turbo / LCM-LoRA) and
**~20–45 s/image** for classic SD 1.5 (20–30 steps). SDXL, SD3, and Flux **do not fit**
4 GB and should be ruled out. The **runtime is the easy part** (ComfyUI already advertises
4 GB VRAM support); the **real work is the Proxmox GPU hand-off and the MyOGChat plumbing**.

Two things to confirm first, because they change everything:
1. **It really is 4 GB** (some GTX 1050s are 2 GB — a 2 GB card makes even SD 1.5 painful).
2. **The card is free** — a GPU bound to the Proxmox host (console/desktop) cannot be
   passed to a VM, and a GPU used by the host is the normal case for LXC.

---

## 2. Hardware reality: GTX 1050 (Pascal)

| Property | Value | Consequence |
|---|---|---|
| Architecture | Pascal, GP107 | **No tensor cores**, no BF16/FP8, no fast FP16 |
| Compute capability | **6.1 (sm_61)** | Still supported by CUDA 12.x only |
| CUDA cores | 640 (1050) / 768 (1050 Ti) | ~1.9 TFLOPS FP32 — the bottleneck |
| FP16 | 1/64 rate on Pascal | **fp16 saves VRAM but does NOT speed up compute** |
| VRAM | 2 GB or **4 GB** (verify!) | 4 GB = SD 1.5 class only |

### CUDA / PyTorch support for Pascal — the hard ceiling
- **CUDA Toolkit 13.0 removed offline compilation and library support for Maxwell, Pascal,
  and Volta** ("Architecture support … is considered feature-complete… newer toolkits will
  be unable to target these architectures"). CUDA **12.x is the last usable toolkit** for
  a GTX 1050. (NVIDIA CUDA 13.0 release notes, §2.6.2)
- **PyTorch cu128 wheels dropped Maxwell + Pascal** (PyTorch issue #157517; shipping
  cu128 builds from 2.8 on no longer target sm_50/sm_60/sm_61). **cu126 wheels still work.**
- ComfyUI ships a **dedicated cu126 portable "for Nvidia 10 series and older GPUs"** and
  explicitly warns *not* to use the cu130 build on 10-series. This is the officially
  supported path for your card.
- **Practical rule: pin PyTorch to a cu126 build (torch ≤ 2.7).** Do not let a naive
  `pip install torch` pull a cu13x/cu128 wheel, or you get
  `CUDA error: no kernel image is available`.

## 3. Does the model fit? (4 GB GTX 1050)

VRAM figures are fp16 weights + 512×512 activations; times are estimates for a GTX 1050,
anchored to a measured GTX 1050 Ti data point (512×512, 20 steps, Euler-a, **31 s** with
ControlNet, 89.8 % VRAM) and the RTX 3050 ComfyUI benchmark (7.2 s @ 512×512/30 steps) —
a 1050 is ~3–4× slower than a 3050.

| Model | Fits 4 GB? | Steps | Est. time (1050, 512²) | Notes |
|---|---|---|---|---|
| **SD 1.5** (fp16) | ✅ tight (~3–4 GB) | 20–30 | **20–45 s** | Baseline. Use fp16 + xformers/SDP + `--lowvram`/medvram if needed |
| **SD 2.1** (fp16) | ✅ (~3–4 GB) | 20–30 | **25–45 s** | Same class as 1.5; base for SD-Turbo |
| **SD-Turbo** (SD2.1 distill) | ✅ comfortable (~1–2 GB) | **1–4** | **~3–8 s** | Best quality/speed trade-off that fits. 512² fixed |
| **LCM-LoRA on SD 1.5** | ✅ | 4–8 | **~6–15 s** | Keeps SD 1.5 ecosystem/checkpoints, few-step sampling |
| **SDXL / SDXL-Turbo** | ❌ | — | — | ~6.9 GB weights; 8 GB cards OOM in benchmarks. Heavy offload = impractical |
| **SD 3 / SD 3.5** | ❌ | — | — | Multi-GB text encoders; way over budget |
| **Flux.1** | ❌ | — | — | 24 GB class |

**Recommendation for the box:** ship **SD-Turbo (or SD 1.5 + LCM-LoRA)** as the default and
keep **SD 1.5** for quality. Both fit and are usable interactively; SDXL/Flux are off the table.

## 4. Runtime choice

| Runtime | 4 GB friendliness | Scriptability | Verdict |
|---|---|---|---|
| **ComfyUI** | Best — auto VRAM management, model offload, *async weight streaming*; README: *"can run even the biggest open source models on as low as 4 GB vram + 8 GB ram"* | HTTP **and** WebSocket API (`/prompt`, `/ws`, `/history/{id}`, `/view`) | **Recommended** |
| AUTOMATIC1111 / Forge | Works (`--lowvram`), Forge is faster/lighter | REST is awkward; no clean queue API | OK, but worse for automation |
| `diffusers` script | Works for SD 1.5/SD-Turbo (`enable_model_cpu_offload`, attention slicing) | Trivial to call from a wrapper | Good for a minimal shim |

**ComfyUI API essentials** (docs.comfy.org, "Server Routes"/"API Examples"):
- `POST /prompt` with `{"prompt": <API-format workflow JSON>, "client_id": <uuid>}` →
  returns `prompt_id` (queue position).
- Wait for completion via **`GET /history/{prompt_id}` polling** (simplest from Go) or the
  `/ws` WebSocket (`executing` event with `node: null`).
- Fetch the PNG: `GET /view?filename=…&subfolder=…&type=output`.
- `GET /system_stats` for a health check / VRAM report.
- Start headless on the LAN: `python main.py --listen 0.0.0.0 --port 8188`.

## 5. Proxmox: how to give the container/VM the GPU

There are two paths. **Both require the GPU to be dedicated to the guest** (a GPU bound to
the host console cannot be passed to a VM).

### Option A — **LXC with device passthrough (recommended for a headless host)**
Simplest when the Proxmox node is a headless server and the 1050 has no desktop duty.
No IOMMU, no vfio, no separate OS, near-native performance.

1. **On the host:** install the NVIDIA driver (`pve-headers` + the Debian non-free
   `nvidia-driver`/`.run`), then verify `nvidia-smi` works **on the host**.
2. Note the device nodes: `ls -l /dev/nvidia*` (`nvidia0`, `nvidiactl`, `nvidia-uvm`,
   `nvidia-uvm-tools`).
3. Edit `/etc/pve/lxc/<id>.conf` (privileged container is simplest):
   ```
   lxc.cgroup2.devices.allow: c 195:* rwm      # /dev/nvidia*
   lxc.cgroup2.devices.allow: c 509:* rwm      # /dev/nvidia-uvm*
   lxc.mount.entry: /dev/nvidia0 dev/nvidia0 none bind,optional,create=file
   lxc.mount.entry: /dev/nvidiactl dev/nvidiactl none bind,optional,create=file
   lxc.mount.entry: /dev/nvidia-uvm dev/nvidia-uvm none bind,optional,create=file
   lxc.mount.entry: /dev/nvidia-uvm-tools dev/nvidia-uvm-tools none bind,optional,create=file
   ```
4. **Inside the container:** install a **matching** driver (or bind-mount the host's
   `libnvidia*` + `nvidia-smi`). Then `nvidia-smi` must work in the container.
5. Install PyTorch **cu126** + ComfyUI, load SD-Turbo/SD 1.5.

⚠️ **Caveat:** host and container driver versions must match; kernel/driver upgrades can
break it. This is a community recipe, not in the official Proxmox wiki.

### Option B — **VM with PCI(e) passthrough (official, isolated, heavier)**
Per the Proxmox wiki "PCI(e) Passthrough" — the robust, documented route:

1. BIOS/UEFI: enable **VT-d/IOMMU**. Kernel cmdline `intel_iommu=on iommu=pt`
   (Intel; AMD enables by default on modern kernels).
2. `/etc/modules-load.d/vfio.conf`: `vfio`, `vfio_iommu_type1`, `vfio_pci`; run
   `update-initramfs -u -k all`.
3. **Free the device from the host:** `options vfio-pci ids=<vendor:device>` (from
   `lspci -nn`) and/or `blacklist nvidia`/`blacklist nouveau`. Reboot.
4. Verify `lspci -nnk` shows `Kernel driver in use: vfio-pci`.
5. Create a VM: **q35 + OVMF (UEFI)**, add **Host PCI** device `01:00` (All Functions).
   The GTX 1050 has a UEFI GOP ROM, so OVMF works. Install Ubuntu + NVIDIA driver + CUDA
   + PyTorch cu126 + ComfyUI inside.

### Recommendation
- **Headless Proxmox host, card unused by host → LXC (Option A).** Least moving parts.
- **Host needs the GPU, or you want isolation / easy rollback → VM (Option B).**
- Either way, put **ComfyUI + the shim in the guest**, never on the Proxmox host.

## 6. Exposing it to MyOGChat

### What already exists (from the repo)
- `TODO.md` **§3.1 Image generation** already scopes this: *"a new provider abstraction +
  `POST /api/images` (prompt, size, model), store generated images as attachments, render
  in chat, track cost"*, and confirms **OpenCode Go has no image-output model** (vision
  input only). Blocker was "a chosen image provider + key" — self-hosting removes the key.
- Backend patterns to reuse: `internal/upstream` (outbound HTTP client), `internal/secret`
  (AES-GCM encrypt/decrypt for stored secrets), `internal/server/integrations.go` (settings
  + admin toggles), `internal/server/server.go` (route registration).
- ⚠️ **Storage gap:** the `attachments` table is **text-only** (`store.Attachment.Text`,
  `Chars()`; `GET /api/attachments/{id}` returns JSON metadata, not bytes). Generated
  images need a new **binary** store — either a `blobs(id, user_id, mime, data BLOB,
  created_at)` table or PNGs on disk — plus a `GET /api/images/{id}` byte endpoint.

### Recommended shape (3 layers)
```
browser ── POST /api/images ──▶ MyOGChat (Go, Pi) ── POST /v1/images/generations ──▶ shim ──▶ ComfyUI (GTX 1050)
                                   (stores PNG, returns id)      Bearer <token>        FastAPI    8188
```
1. **Shim on the Proxmox box** — a tiny FastAPI/Flask app (or use an existing
   OpenAI-compatible ComfyUI shim) that accepts an **OpenAI Images-style** request and
   drives ComfyUI (or a `diffusers` pipeline). Making it OpenAI-compatible means the same
   Go provider also works later against OpenAI/Replicate — matches the §3.1 plan.
2. **MyOGChat provider** — one `POST /api/images` handler + a provider interface. For the
   self-hosted provider, call the shim; store the PNG; return `{ "id": "...", "url":
   "/api/images/<id>" }`; the SPA renders `<img src="/api/images/<id>">`.

### Wire format
**MyOGChat → shim** (`POST http://<pve-lan-ip>:8080/v1/images/generations`):
```json
{ "model": "sd-turbo", "prompt": "a red fox in a snowy forest", "size": "512x512",
  "n": 1, "response_format": "b64_json" }
```
Headers: `Authorization: Bearer <MYOGCHAT_IMAGE_TOKEN>`, `Content-Type: application/json`.
**Shim → MyOGChat:**
```json
{ "created": 1760000000, "data": [ { "b64_json": "<base64 PNG>" } ] }
```
The shim internally maps `{prompt,size,steps}` onto a **fixed API-format workflow**
(SD-Turbo = 1–4 steps, `guidance_scale=0`; SD 1.5 = 20–30 steps), submits to `/prompt`,
polls `/history/{prompt_id}`, then `GET /view` for the PNG.

**MyOGChat's own endpoint** (`POST /api/images`): `{ "prompt", "size", "steps"?,
"model"? }` → returns `{ "id", "url" }` (auth via the existing session cookie; reuse the
admin Integrations settings to store the box URL + token).

### Auth & network
- **Shared bearer token** on the shim (LAN-only, e.g. `MYOGCHAT_IMAGE_TOKEN`); store it
  encrypted in MyOGChat via `internal/secret`. Constant-time compare on the shim.
- **Do NOT expose the shim through the Cloudflare Tunnel.** Keep MyOGChat's public
  hostname → Pi → LAN → shim. Optional: mTLS or an SSH tunnel if the box is off-LAN.
- Add a health probe (`GET /system_stats` on ComfyUI) so Settings can show "online".

## 7. If 4 GB is too tight (fallbacks, in order)
1. **SD-Turbo / LCM-LoRA at 512×512, 1–8 steps** — the single biggest win (~3–15 s).
2. **Drop resolution** to 384–448² for SD 1.5 (VRAM ∝ tokens); upscale after if needed.
3. **Aggressive offload** in ComfyUI (`--lowvram`) — works but slow; Forge is a lighter A1111.
4. **External free/cheap provider** if the GPU disappoints: Cloudflare Workers AI (free
   tier), Pollinations (free), or Replicate/fal.ai (Flux/SDXL, pay-per-image). The
   OpenAI-compatible shim interface above makes swapping trivial.
5. **The Raspberry Pi 4B cannot do this** — no GPU; CPU SD 1.5 is minutes/image. Keep
   image gen on the Proxmox box only.

---

## 8. Go / No-Go

**GO**, with these expectations:
- **Quality:** good 512×512 SD 1.5/SD-Turbo output — fine for a personal chat assistant.
  Not photoreal SDXL/Flux quality.
- **Speed:** ~**5–15 s** (SD-Turbo/LCM) to ~**20–45 s** (SD 1.5, 20–30 steps) per image.
  Usable, not instant.
- **Cost:** electricity only; no per-image API fees.
- **Effort:** mostly **infrastructure** — GPU hand-off (LXC or vfio) + driver pinning to
  **cu126/PyTorch ≤2.7** + the shim + a small MyOGChat `POST /api/images` feature and a
  binary blob store. The model/runtime side is the easy half.
- **Biggest risks:** the card is actually 2 GB; the card is needed by the host console;
  a naive PyTorch/CUDA upgrade silently breaks Pascal (pin cu126).

**Decide after one measurement:** run SD-Turbo on the box and time it. If you get a
512×512 image in <15 s, proceed. If it's >60 s even with SD-Turbo, go external.
