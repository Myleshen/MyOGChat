# Image generation on the Proxmox box `asus-rog` — recheck for the **GTX 1650 Ti Mobile** (Turing)

**Supersedes** `docs/research/3.1-imagegen-proxmox.md` / `research-imagegen-proxmox.md`.
The earlier report assumed a **GTX 1050 (Pascal, sm_61)**. The actual GPU is an
**NVIDIA GeForce GTX 1650 Ti Mobile (TU117, Turing, compute capability 7.5, 4 GB GDDR6)**.
Most of the Pascal-specific constraints in that report **do not apply**. This report
re-derives feasibility from primary sources and gives a definitive go/no-go.

**Question:** can this 4 GB Turing laptop GPU in a Proxmox VE host run a local image
model and serve it to MyOGChat (Go + embedded SPA on a Pi 4B) without an external image API?

---

## 0. TL;DR verdict

**GO.** Turing (sm_75) is the **baseline** architecture for current CUDA 13.x and current
PyTorch wheels, so the Pascal "pin cu126 / torch ≤ 2.7 / CUDA 12.x max" advice is **wrong
for this card and must be dropped**. FP16 runs at **2× FP32** (not Pascal's 1/64), so
half-precision actually speeds generation up. Fit and speed are governed only by the
**4 GB VRAM**:

- **SD-Turbo / LCM-LoRA (SD 1.5)** → comfortable, **~6–12 s** at 512². Best default.
- **SD 1.5 / SD 2.1** → tight but workable, **~18–35 s** at 512² (20–30 steps).
- **SDXL / SDXL-Turbo** → **do not fit** 4 GB (offload-only, ~1 min+); rule out.
- **SD 3 / Flux** → way over budget; rule out.

Recommended stack: **ComfyUI** (dynamic VRAM + async offload, clean HTTP API) on the host
driver via an **LXC device passthrough** (simplest, since `nvidia-driver 615.71.09` is already
loaded), fronted by a tiny **OpenAI-compatible shim** (`POST /v1/images/generations`,
bearer token, LAN-only). App side adds `POST /api/images`, a **binary image store**
(`attachments` is text-only), and `GET /api/images/{id}`.

**Gate:** time one SD-Turbo 512² image. **< 15 s → proceed.** (Anchor benchmarks say ~10 s,
so this should pass, but the *first* (cold) run includes model load — measure a warm run.)

## 1. Corrections to the prior (Pascal) report

| Prior claim (GTX 1050 / Pascal) | Correct for GTX 1650 Ti Mobile (Turing) |
|---|---|
| "CUDA 12.x is the last usable toolkit" | **False here.** CUDA 13.0's *minimum* supported CC is **7.5** = Turing. Turing is fully supported by CUDA 13.x. The CUDA 13 removal targets **pre-7.5**: Maxwell, Pascal, Volta. |
| "Pin PyTorch to a cu126 build (torch ≤ 2.7)" | **Not needed.** PyTorch 2.8+ `cu128` wheels ship `SM_75` (and `SM_70/80/86/89/90/100/120`). Current `cu128`/`cu130` wheels run on Turing. |
| "ComfyUI cu126 portable for 10-series" | That build is for **pre-Turing**. Turing uses the **normal current CUDA build**. |
| "FP16 = 1/64 rate, fp16 saves VRAM but not compute" | **False here.** Turing GTX 16-series runs FP16 at **2× FP32** via dedicated FP16 cores. FP16 **does** speed compute up. |
| "~20–45 s SD 1.5; ~3–8 s SD-Turbo" | Similar order of magnitude, but Turing is a bit stronger; measured anchors give SD-Turbo ~10 s, SD 1.5 ~20 s. |
| Model fit conclusions | **Unchanged** — the binding constraint is 4 GB, which is the same on both cards. |

**Bottom line:** the "hard ceiling" the previous report worried about was an artifact of
Pascal. On Turing the CUDA/PyTorch ceiling is gone; only VRAM remains.

## 3. CUDA / PyTorch support for Turing — the ceiling is gone

**CUDA 13.x supports Turing as its minimum.**
NVIDIA's own developer blog and the CUDA 13 release notes state that CUDA 13.0 removes
*offline compilation* support for architectures **before** CC 7.5 — i.e. Maxwell, Pascal,
and Volta — and that `nvcc --list-gpu-arch` on CUDA 13 starts at `compute_75`. Turing
(`sm_75`) is therefore the **baseline**, not deprecated. ("Navigating GPU Architecture
Support", NVIDIA Technical Blog; CUDA 13.0 Release Notes §2.6.2.)

**PyTorch current wheels include sm_75.**
PyTorch 2.8.0 `cu128` dropped only Maxwell/Pascal (`sm_50`/`sm_60`). The supported set from
2.8 on is `SM_70, SM_75, SM_80, SM_86, SM_89, SM_90, SM_100, SM_120`. PyTorch 2.11 later
dropped **Volta** (`sm_70`) from `cu128`/`cu129`, but **Turing (`sm_75`) remains**. So
`cu126`, `cu128`, and `cu130` wheels all work; **no pinning is required**. (PyTorch
release notes / 2.8.0 notes; Qualiteg compatibility table.)

**ComfyUI.** Use the **current stable** ComfyUI with a **normal current CUDA PyTorch build**
(`cu128` recommended; `cu130` also fine given the host driver is a 6xx branch). Do **not**
reach for the "10-series and older" portable — that exists for Pascal, not Turing.

**Driver.** The host already has `nvidia-driver 615.71.09` (a 6xx-branch driver, well past
the CUDA 13.0 threshold of 580). Userspace in the container only needs to **match 615.x**.

### Chosen build

| Component | Choice | Why |
|---|---|---|
| CUDA runtime | 12.8 or 13.x (`cu128` / `cu130`) | `sm_75` supported; driver 615 is new enough |
| PyTorch | current stable (`cu128`) | `SM_75` in the shipped arch list |
| Precision | **fp16** (`--force-fp16` / `--fp16-unet` + `--fp16-text-enc`) | Turing has 2× fp16; no bf16/fp8 |
| ComfyUI | current stable | dynamic VRAM + async offload; HTTP API |

## 4. FP16 throughput on GTX 16-series — **2×, not 1/64**

This is the single biggest correction. Pascal GeForce crippled FP16 to 1/64 of FP32;
**Turing GTX 16-series does not** — it runs FP16 at **2× FP32** through dedicated FP16 units.

- Tom's Hardware (GTX 1660 Ti / TU116): *"Nvidia says it replaces Turing's Tensor cores
  with 128 dedicated FP16 cores per SM, which allow GeForce GTX 1660 Ti to process
  half-precision operations at 2x the rate of FP32. The other Turing-based GPUs boast
  double-rate FP16 as well."* The article quotes **5.4 TFLOPS FP32 / 10.9 TFLOPS FP16**.
- The Wikipedia GeForce 16-series spec table lists GTX 1650 Ti (Laptop) as
  **FP16 5530–6083 GFLOPS vs FP32 2765–3041 GFLOPS** — exactly 2×.
- NVIDIA's Turing whitepaper lists 2× FP16 for the RTX parts (e.g. 2080 Ti 14.2 FP32 /
  28.5 FP16); the 16-series keeps the same SM FP16 datapath minus the tensor cores.

**Consequence for speed:** running SD in fp16 roughly halves the per-step compute versus
fp32, and halves the weights/activations in VRAM. This is the opposite of the Pascal
situation and is why a 3 TFLOPS FP32 card can still do SD-Turbo in ~10 s.

**Caveat (Turing-specific):** because there are no bf16/fp8 tensor cores, if ComfyUI picks
a **bf16** compute dtype it silently falls back to **fp32** (≈3.4× slower on Turing).
Always pin **fp16** for SD 1.5 / SD 2.1 / SD-Turbo (they are fp16-native).

## 5. VRAM fit (4 GB) and realistic 512×512 times

Weights are fp16; activations are for 512×512. "Fits" means ComfyUI's dynamic VRAM +
async offload can keep the working set inside 4 GB without disk thrash.

| Model | Fits 4 GB? | Steps | Est. 512² time | Notes |
|---|---|---|---|---|
| **SD-Turbo** (SD 2.1 distill, 0.9B) | ✅ comfortable (~1.5–2.5 GB) | **1–4** | **~8–12 s** | Best default. 512² fixed, `guidance_scale=0.0` (cfg≈1.0). |
| **LCM-LoRA on SD 1.5** | ✅ (~3–4 GB) | 4–8 | **~6–12 s** | Keeps the SD 1.5 checkpoint ecosystem; few-step sampling. |
| **SD 1.5** (fp16) | ✅ tight (~3–4 GB) | 20–30 | **~18–35 s** | Baseline quality. Offload the text encoder. |
| **SD 2.1** (fp16) | ✅ tight (~3–4 GB) | 20–30 | **~20–35 s** | Same class as 1.5; base for SD-Turbo. |
| **SDXL-Turbo** | ❌ (offload-only) | 1–4 | ~40 s+ at 512²; 256² ≈ 10 s | ~6.9 GB fp16 weights → constant offload; not interactive. |
| **SDXL 1.0** | ❌ | 20–30 | ~1 min+ (offload) | Does not fit; grade "won't fit" on 4 GB. |
| **SD 3 / 3.5** | ❌ | — | — | Multi-GB text encoders. |
| **Flux.1** | ❌ | — | — | 24 GB class. |

**Anchors used** (measured, public):
- willitrunai GTX 1650 4 GB: **SD-Turbo 512² ≈ 10.4 s**, SD 1.5 512×768 ≈ 20.8 s,
  **LCM DreamShaper 512×768 ≈ 6.2 s**, SDXL 1.0 fp16 "won't fit (~1 m 23 s)".
- Novita GTX 1650 guide: SD 1.5 512² ≈ **15 s** (DPM++ 2M Karras).
- GigaGPU ComfyUI fp16 512²/30 steps: **RTX 3050 = 7.2 s** (a 3050 has ~3× the 1650 Ti
  Mobile's FP32 and tensor cores ⇒ ~20 s on this card, consistent with the table).
- The GTX 1650 Ti Mobile is roughly a **T4-class Turing part with ~1/3 the FP32** and no
  tensor cores; a T4 does SD 1.5 512²/20 steps in a few seconds, so a few tens of seconds
  here is expected.

**Practical recommendation:** default to **SD-Turbo** (fastest, fits comfortably); keep
**SD 1.5 + LCM-LoRA** for a few-step "quality" option; keep plain **SD 1.5** for 20–30-step
renders. SDXL/Flux are out.

## 6. Runtime choice

| Runtime | 4 GB friendliness | Scriptability | Verdict |
|---|---|---|---|
| **ComfyUI** | Best — **dynamic VRAM** (enabled by default on NVIDIA) + **async weight offloading**; unloads models between runs; `/free` endpoint | Clean HTTP API (`/prompt`, `/history/{id}`, `/view`, `/system_stats`) + WebSocket | **Recommended** |
| AUTOMATIC1111 / Forge | Works with `--lowvram`; Forge is lighter | Awkward REST; no clean queue | Worse for automation |
| `diffusers` script | Works (`enable_model_cpu_offload`, attention slicing) | Trivial to wrap | Fine for a minimal shim, but re-implements what ComfyUI does |

**Start headless on the LAN:**
```
python main.py --listen 0.0.0.0 --port 8188 --disable-auto-launch \
  --force-fp16 --reserve-vram 0.5
```

**VRAM / precision flags that matter on this card** (from the ComfyUI Startup Flags doc):
- `--force-fp16` (or `--fp16-unet --fp16-text-enc`) — **required**; avoid bf16/fp8 fallback.
- `--reserve-vram 0.5` — leave headroom for the driver/OS on a 4 GB card.
- Dynamic VRAM is **on by default** on NVIDIA; async offload is **on by default**. You
  generally do **not** need `--lowvram`. If a 20-step SD 1.5 run OOMs, fall back to
  `--lowvram` (runs the text encoder on CPU), then `--novram` (last resort).
- Do **not** pass `--normalvram` (not a real flag). `--gpu-only/--highvram/--lowvram/--novram/--cpu`
  are mutually exclusive.
- `--cache-none` if you want every run to be a clean, comparable measurement (slower).

**ComfyUI API essentials** (Server Routes doc): `POST /prompt` with `{"prompt": <API-format
workflow>, "client_id": <uuid>}` → `prompt_id`; poll `GET /history/{prompt_id}` (or use the
`/ws` `executing` event with `node: null`) → read `outputs[<node>].images[]` → fetch bytes
with `GET /view?filename=…&subfolder=…&type=output`. `GET /system_stats` is a good health
probe.

**Fixed SD-Turbo workflow (API format)** the shim will submit:
```json
{
  "4": {"class_type":"CheckpointLoaderSimple","inputs":{"ckpt_name":"sd_turbo.safetensors"}},
  "5": {"class_type":"EmptyLatentImage","inputs":{"width":512,"height":512,"batch_size":1}},
  "6": {"class_type":"CLIPTextEncode","inputs":{"text":"<PROMPT>","clip":["4",1]}},
  "7": {"class_type":"CLIPTextEncode","inputs":{"text":"","clip":["4",1]}},
  "3": {"class_type":"KSampler","inputs":{"seed":0,"steps":2,"cfg":1.0,
        "sampler_name":"euler_ancestral","scheduler":"normal","denoise":1.0,
        "model":["4",0],"positive":["6",0],"negative":["7",0],"latent_image":["5",0]}},
  "8": {"class_type":"VAEDecode","inputs":{"samples":["3",0],"vae":["4",2]}},
  "9": {"class_type":"SaveImage","inputs":{"filename_prefix":"myogchat","images":["8",0]}}
}
```
(SD-Turbo uses `guidance_scale=0.0` in diffusers ≈ `cfg: 1.0` in ComfyUI; SD 1.5 uses
`cfg: 7`, 20–30 steps.)

## 7. Proxmox deployment

Host facts already verified: driver `615.71.09` loaded, `/dev/nvidia0` + `/dev/nvidiactl`
present, `intel_iommu=on iommu=pt`, `vfio-pci` available, GPU in **IOMMU group 2** (with its
audio function + root port — the "OK" grouping per the Proxmox wiki), `cuda-keyring`
present, **no GPU currently assigned to any VM/LXC**.

### Recommended: LXC with device passthrough (Option A)

The host driver is already loaded and the GPU is idle, so **sharing the host kernel driver
into an LXC is the least-moving-parts path**. No VFIO, no exclusive ownership, near-native
performance, and it works even if the host keeps the dGPU powered.

Outline:
1. **Host:** confirm the device nodes exist and load `nvidia-uvm`:
   `ls -l /dev/nvidia*` (expect `nvidia0`, `nvidiactl`, `nvidia-uvm`, `nvidia-uvm-tools`,
   `nvidia-caps/nvidia-cap1..2`). Run `nvidia-modprobe -c0 -u` (or `nvidia-smi -L`) once to
   create `nvidia-uvm`. Add a udev rule / systemd unit so it survives reboots (a common
   gotcha: `/dev/nvidia-uvm` is missing after reboot until something opens the GPU).
2. **Container conf** (`/etc/pve/lxc/<id>.conf`) — use the **Proxmox UI "Add → Device
   Passthrough"** (PVE 8.2+) which writes cgroups for you, or manually:
   ```
   lxc.cgroup2.devices.allow: c 195:* rwm    # /dev/nvidia0, nvidiactl
   lxc.cgroup2.devices.allow: c 243:* rwm    # nvidia-uvm (major may be 243/509/510)
   lxc.cgroup2.devices.allow: c 234:* rwm    # nvidia-caps (major varies; check host)
   lxc.mount.entry: /dev/nvidia0 dev/nvidia0 none bind,optional,create=file
   lxc.mount.entry: /dev/nvidiactl dev/nvidiactl none bind,optional,create=file
   lxc.mount.entry: /dev/nvidia-uvm dev/nvidia-uvm none bind,optional,create=file
   lxc.mount.entry: /dev/nvidia-uvm-tools dev/nvidia-uvm-tools none bind,optional,create=file
   lxc.mount.entry: /dev/nvidia-caps dev/nvidia-caps none bind,optional,create=dir
   ```
   **Check the major numbers on the host** (`ls -l /dev/nvidia*`) — `nvidia-uvm` is not
   always 243 and `nvidia-caps` is not always 234.
3. **Container userspace:** install the **same** driver version (`615.71.09`) *without* the
   kernel module — i.e. the `.run` installer with `--no-kernel-module`, or bind-mount the
   host's `libnvidia*.so*` + `nvidia-smi`. **Version mismatch = `Failed to initialize
   NVML` / driver/library mismatch.** Then `nvidia-smi` must succeed inside the container.
4. **Inside the container:** install ComfyUI + PyTorch `cu128`, load SD-Turbo / SD 1.5,
   run `python main.py --listen 0.0.0.0 --force-fp16 --reserve-vram 0.5`.

Gotchas:
- **Driver version match** is the #1 failure. Container libs must equal host `615.71.09`.
- **`nvidia-uvm` creation** after reboot (see step 1).
- **Unprivileged containers** need the driver installed **without kernel modules**; the
  cgroup majors above are the host's, and `optional` on the mount entries hides mistakes.
- A naive **kernel/driver upgrade** on the host breaks the container until its userspace is
  re-matched. Pin both.

### Alternative: VFIO VM passthrough (Option B)

Per the Proxmox "PCI(e) Passthrough" wiki — the official, isolated route:
1. BIOS/UEFI VT-d/IOMMU on; kernel cmdline `intel_iommu=on iommu=pt` (already set).
2. `/etc/modules-load.d/vfio.conf`: `vfio`, `vfio_iommu_type1`, `vfio_pci`; `update-initramfs -u -k all`.
3. Free the device from the host: `options vfio-pci ids=<vendor:device>` (from `lspci -nn`)
   and/or `blacklist nvidia`; reboot; verify `lspci -nnk` shows `Kernel driver in use: vfio-pci`.
4. VM: **q35 + OVMF**, `hostpci0: 01:00,pcie=on` (All Functions — GPU + audio).
5. Install Ubuntu + NVIDIA driver + CUDA + PyTorch + ComfyUI inside.

**Laptop/Optimus caveats (important for a 1650 Ti Mobile):**
- The dGPU is a laptop part muxed behind the Intel iGPU in Optimus/hybrid mode. For
  **compute-only** (CUDA) this is fine — no display output is needed (the Proxmox wiki notes
  framebuffer passthrough isn't required for CUDA/OpenCL accelerators).
- Mobile vBIOS may not expose a clean **UEFI GOP** ROM, and the dGPU may **not reset
  cleanly (FLR)** on VM shutdown. This is the main reason to prefer LXC here.
- If VFIO is used, you may need a dumped vBIOS `romfile=` and to keep the GPU unused by the
  host console.

### Recommendation
Use **Option A (LXC)**. It matches the host state (driver already loaded), avoids the
laptop vBIOS/reset risks, and keeps ComfyUI + the shim off the Proxmox host itself.

## 8. MyOGChat integration

### Current app facts (from the repo)
- Go stdlib `net/http` only; single dep `modernc.org/sqlite`; `CGO_ENABLED=0`, arm64.
- `attachments` table is **text-only** (`store.Attachment.Text`, `Chars()`); `GET
  /api/attachments/{id}` returns JSON metadata, **not bytes**. So generated images need a
  **new binary store** + a byte endpoint.
- Patterns to reuse: `internal/upstream` (outbound HTTP), `internal/secret`
  (AES-256-GCM `Encrypt`/`Decrypt`), `internal/server/integrations.go` (settings + admin
  toggles), `internal/server/server.go` (routes), the `janitor` in `main.go` (retention).
- `TODO.md` §3.1 already scopes `POST /api/images` and confirms OpenCode Go has **no
  image-output model** (vision input only).

### Three layers
```
browser ── POST /api/images ─▶ MyOGChat (Go, Pi) ── POST /v1/images/generations ─▶ shim ─▶ ComfyUI (GTX 1650 Ti)
           (stores PNG bytes, returns id)   Bearer <token>, LAN-only        FastAPI  :8080   :8188
```

### (a) Shim on the Proxmox box — OpenAI-compatible
A tiny FastAPI/Flask app (`/opt/myogchat-image/shim.py`) that:
- authenticates `Authorization: Bearer <MYOGCHAT_IMAGE_TOKEN>` (constant-time compare),
- maps the request to a **fixed API-format workflow**, submits to ComfyUI `/prompt`,
- polls `GET /history/{prompt_id}` (or the `/ws` `executing` event), then `GET /view`,
- returns the PNG as `b64_json`.

**Request (MyOGChat → shim):**
```http
POST http://<pve-lan-ip>:8080/v1/images/generations
Authorization: Bearer <MYOGCHAT_IMAGE_TOKEN>
Content-Type: application/json
```
```json
{ "model": "sd-turbo", "prompt": "a red fox in a snowy forest",
  "size": "512x512", "n": 1, "response_format": "b64_json" }
```

**Response (shim → MyOGChat):**
```json
{ "created": 1760000000,
  "data": [ { "b64_json": "<base64 PNG>" } ] }
```

Making the shim **OpenAI-Images-compatible** means the same Go provider also works later
against OpenAI/Replicate — matching the §3.1 plan. Sketch:
```python
@app.post("/v1/images/generations")
def generate(req):
    check_bearer(req)
    wf = sd_turbo_workflow(prompt=req.prompt, w=512, h=512, steps=2)
    pid = comfy_post("/prompt", {"prompt": wf, "client_id": CLIENT_ID})["prompt_id"]
    meta = wait_history(pid)                       # poll /history/{pid}
    png  = comfy_get("/view", **meta["images"][0]) # filename/subfolder/type
    return {"created": int(time.time()),
            "data": [{"b64_json": base64.b64encode(png).decode()}]}
```

### (b) MyOGChat provider
One new package `internal/images` with a client (stdlib `net/http`) that POSTs to the shim
with the bearer token and decodes `b64_json`. Keep it behind a small interface so an
external OpenAI Images provider can be dropped in later.

### (c) App endpoints + binary store
New routes in `internal/server/server.go`:
```
POST   /api/images          → { "prompt", "size"?, "model"?, "steps"? } → { "id", "url", "width", "height" }
GET    /api/images/{id}     → image/png bytes (owner-scoped)
DELETE /api/images/{id}     → 204
```
`GET /api/images/{id}` writes raw bytes with `Content-Type: image/png` and a long cache
header (the SPA renders `<img src="/api/images/<id>">`).

**Binary store** — a new table in `internal/store` (mirrors the `attachments` migration
pattern; additive, safe on existing DBs):
```sql
CREATE TABLE IF NOT EXISTS images (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  prompt     TEXT NOT NULL,
  model      TEXT,
  mime       TEXT NOT NULL,
  width      INTEGER NOT NULL,
  height     INTEGER NOT NULL,
  size       INTEGER NOT NULL,
  data       BLOB NOT NULL,          -- the PNG bytes
  created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_images_user ON images(user_id);
```
- Methods: `InsertImage`, `GetImage(id, userID)` (owner guard → `ErrNotFound`), `DeleteImage`,
  and `DeleteImagesOlderThan` wired into the existing **`janitor`** in `main.go` next to
  `DeleteAttachmentsOlderThan`.
- BLOBs are fine at personal scale (a 512² PNG is a few hundred KB). If DB size ever becomes
  a concern, swap `data BLOB` for a path on disk behind the same methods — the API is unchanged.

**Settings** (`internal/server/integrations.go`): add `image_enabled` (admin toggle),
`image_shim_url`, and `image_shim_token` (stored encrypted via `internal/secret`, exposed to
the SPA only as `image_shim_configured` + a `keyHint`). Add a health probe against ComfyUI
`GET /system_stats` so Settings can show "online".

### Auth & network
- Shared bearer token on the shim, LAN-only. **Do not expose the shim through the Cloudflare
  Tunnel** — keep MyOGChat's public hostname → Pi → LAN → shim. Store the token encrypted.
- Optional mTLS or an SSH tunnel if the box is ever off-LAN.

## 10. Timing gate

**Measure one SD-Turbo 512² image end-to-end and time it.** Report both a **cold** run
(includes model load — will be slower) and a **warm** run (model resident).

- **< 15 s warm → PROCEED** with the full integration.
- **15–30 s → proceed with SD-Turbo/LCM only**; expect SD 1.5 to be ~20–35 s (acceptable for
  an async chat feature).
- **> 60 s even warm with SD-Turbo → go external** (the interface is OpenAI-compatible, so
  swapping providers is trivial).

Anchor expectation from public benchmarks: **~10 s**, so the gate should pass comfortably.
Also watch thermals — a 50–80 W laptop dGPU can throttle under sustained load; measure after
a few warm-up images, not on the first one.
