# Google Calendar access without user OAuth consent — research report

**Scope:** MyOGChat (self-hosted Go PWA, single owner, **personal `@gmail.com`** account) wants to
read and create Google Calendar events without going through the user-OAuth consent-screen
process (which, in Testing mode, expires refresh tokens every 7 days and, for restricted scopes,
requires Google verification).

**Question asked:** *"Is there no other way?"*

**Short answer:** Yes. For a single-owner personal account there are two practical non-consent
routes — a **service account whose email is granted access to the calendar** (read **and** write)
and the **per-calendar "Secret address in iCal format"** (read-only, zero credentials). CalDAV is
*not* a way out (OAuth2 is mandatory there). Bridges still need OAuth for writes. User OAuth is
only truly unavoidable if you need per-event attendee invitations without domain-wide delegation,
push notifications tied to a user identity, or access to many calendars you don't control.

---

## 1. Service account + calendar sharing (recommended for read/write)

### 1.1 Does it work for a personal (non-Workspace) Gmail calendar?

**Yes.** A service account (SA) is a Google Cloud identity with its own email
(`name@project.iam.gserviceaccount.com`). Google Calendar sharing is an **ACL grant to an email
address**, not a Workspace-only feature. The owner opens *Settings and sharing → Share with
specific people or groups → Add people and groups*, pastes the SA email, and picks a permission
level. No Admin console, no domain-wide delegation (DWD), no consent screen.

This is well established in practice: the SA email is added as a normal grantee and the primary
calendar's ID is the owner's Gmail address
([Medium walkthrough](https://medium.com/product-monday/accessing-google-calendar-api-with-service-account-a99aa0f7f743);
[Google Calendar community thread](https://support.google.com/calendar/thread/9756319/how-do-i-set-permissions-make-changes-to-events-to-service-account-email?hl=en)
where the resolution was "add the `client_email` value" as a grantee).

The Google Calendar sharing model documents grantees as "another individual user, a user group, a
domain, or the public", and roles `reader` / `writer` / `owner`
([Calendar sharing](https://developers.google.com/workspace/calendar/api/concepts/sharing)).

### 1.2 Permission level → what the app can do

The Calendar UI "Make changes to events" maps to the ACL `writer`-family roles. The API role table
([Calendar sharing](https://developers.google.com/workspace/calendar/api/concepts/sharing)):

| UI option | API role | Read | Create/update/delete events | See private events |
|---|---|---|---|---|
| See only free/busy | `freeBusyReader` | free/busy only | ✗ | ✗ |
| See all event details | `reader` | ✓ | ✗ | ✗ |
| **Make changes to events** | `writerWithoutPrivateAccess` | ✓ | ✓ (non-private) | busy blocks only |
| Make changes and see event details | `writer` | ✓ | ✓ | ✓ |
| Make changes and manage sharing | `owner` | ✓ | ✓ | ✓ (also edits ACLs) |

So **yes, the app can create, update, and delete events** if the owner grants at least
"Make changes to events" (`writerWithoutPrivateAccess`) or "Make changes and see event details"
(`writer`). Deleting an event is an ordinary `events.delete` on a calendar the SA can write to.

### 1.3 Caveats (important)

1. **The SA has no calendar of its own that the owner can see.** The SA can only touch calendars
   that were *explicitly shared with its email*. The app must address the calendar by its known
   `calendarId` (the owner's Gmail address for the primary calendar, or the ID from
   *Settings → Integrate calendar*), not by listing "my calendars".
2. **Sharing no longer auto-inserts into the grantee's `CalendarList`.** Per the sharing docs:
   *"Sharing a calendar with a user no longer automatically inserts the calendar into their
   `CalendarList`."* For an SA this is irrelevant anyway — just call
   `GET /calendars/{calendarId}/events` directly.
3. **Service accounts cannot invite attendees without domain-wide delegation.** Creating an event
   *with attendees* returns `403` `forbiddenForServiceAccounts` —
   *"Service accounts cannot invite attendees without Domain-Wide Delegation of Authority."*
   ([Google Calendar community](https://support.google.com/calendar/thread/299552457/service-accounts-cannot-invite-attendees-without-domain-wide-delegation-of-authority?hl=en);
   [SO #60760959](https://stackoverflow.com/questions/60760959/google-calendar-api-service-account-error)).
   Events **without** attendees (or with the owner as a plain field, not an invitation) work fine.
   This is the single biggest functional limitation of the SA route.
4. **Quota.** A service account is charged as **one user** against the per-minute per-user quota
   (600 req/min/project); the project-wide limit is 10,000 req/min and a 1,000,000 req/day billing
   threshold ([Calendar API usage limits](https://developers.google.com/workspace/calendar/api/guides/quota)).
   For a single-owner app this is a non-issue, but use `quotaUser` if you ever fan out. Handle
   `403 usageLimits` / `429` with truncated exponential backoff.
5. **Not applicable:** domain-wide delegation — that is a Workspace-only admin feature and cannot
   be used with a personal `@gmail.com` account
   ([service-account OAuth doc](https://developers.google.com/identity/protocols/oauth2/service-account)).
6. **Long-lived credential.** The JSON private key does not expire on its own. It is a bearer
   secret that must be encrypted at rest and rotatable. (Google does not keep a copy.)

### 1.4 Exact auth flow (JWT → access token)

Per [Using OAuth 2.0 for Server to Server Applications](https://developers.google.com/identity/protocols/oauth2/service-account):

1. **Build a JWT** with header `{"alg":"RS256","typ":"JWT","kid":"<private_key_id>"}` and claim set:

   ```json
   {
     "iss": "<client_email>",
     "scope": "https://www.googleapis.com/auth/calendar",
     "aud": "https://oauth2.googleapis.com/token",
     "iat": <now>,
     "exp": <now + 3600>
   }
   ```

   *No `sub` claim* — `sub` is only for DWD impersonation, which does not apply here.

2. **Sign** the base string `base64url(header) + "." + base64url(claims)` with **RSASSA-PKCS1-v1_5
   + SHA-256** using the RSA private key from the JSON key file. Signature is base64url-encoded.
3. **Exchange** the signed JWT for an access token:

   ```
   POST https://oauth2.googleapis.com/token
   Content-Type: application/x-www-form-urlencoded

   grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=<signed JWT>
   ```

   Response: `{"access_token":"...","token_type":"Bearer","expires_in":3600}`.
4. **Call the API** with `Authorization: Bearer <access_token>`, e.g.
   `GET https://www.googleapis.com/calendar/v3/calendars/{calendarId}/events`.
5. **On expiry** (`expires_in` ≈ 3600 s) simply re-sign a new JWT and repeat — there is **no refresh
   token** and nothing to persist beyond the key file. Token minting is stateless.

Scopes to use: `https://www.googleapis.com/auth/calendar` (full read/write) or the narrower
`.../calendar.events` ([Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth)).

### 1.5 Implementable with Go stdlib only? **Yes.**

No `google.golang.org/api` / `golang.org/x/oauth2` needed:

- `crypto/rsa` + `crypto/x509` — parse the PEM PKCS#8 private key from the JSON.
- `crypto/sha256` + `crypto/rsa.SignPKCS1v15` (or `SignPSS`; PKCS1v15 matches `RS256`) — sign.
- `encoding/base64` (`RawURLEncoding`) — JWT segment encoding.
- `encoding/json` — header/claims/response parsing.
- `net/http` + `net/url` — token POST and API calls.
- `time` — `iat`/`exp`.

The only care points are correct base64url (no padding, no newlines) and clock skew (`exp` ≤ 1 h
after `iat`, and `exp - iat` must not exceed ~65 min; sync via NTP — the docs list clock skew as a
common `invalid_grant` cause). The docs recommend client libraries "due to the complexity and
security risks" of hand-signing JWTs, but the JWT-bearer flow is small and well-specified.

### 1.6 Setup burden

GCP project → enable **Google Calendar API** → create service account → create JSON key (download
once) → copy `client_email` → in Google Calendar share the calendar with that email at
"Make changes to events". Roughly 5–10 minutes, no consent screen, no verification, no 7-day
expiry.

## 2. Read-only "Secret address in iCal format" (recommended for read-only)

### 2.1 Exists and how to get it

Every Google Calendar (including personal `@gmail.com`) exposes a **Secret address in iCal
format** ([Sync your calendar with computer programs](https://support.google.com/calendar/answer/37648)):

> Settings → *Settings for my calendars* → select the calendar → **Integrate calendar** →
> **Secret address in iCal format** → copy.

The URL looks like:

```
https://calendar.google.com/calendar/ical/<calendarId>/private-<hash>/basic.ics
```

The `private-<hash>` segment is the capability token. If it leaks, the owner clicks **Reset** to
invalidate the old URL and mint a new one.

### 2.2 Properties

- **No OAuth at all.** The URL *is* the credential (bearer-in-URL). Unauthenticated HTTP GET.
- **Read-only.** It serves the calendar's events as iCalendar (RFC 5545); there is no write path.
- **Not the "Public address."** The public `.../public/basic.ics` requires making the calendar
  public. The secret address works without public sharing
  ([Schedule Caddie](https://schedulecaddie.com/how-to/google-calendar-secret-address)).
- **Content is generated server-side and near-current**, but consumers/caches apply their own
  refresh schedules. Google's own *subscription* refresh of external feeds runs every 12–24 h with
  no user control ([Calfeed](https://calfeed.ai/learn/ics-refresh-rate-apple-google)); community
  reports for Google feed caching range from a couple of hours to a few days. There is **no push**,
  no ETag/`If-None-Match` guarantee, and no documented freshness SLA — treat it as eventually
  consistent (minutes to hours), not real-time.

### 2.3 Limitations

- **Read-only** — cannot create/update/delete.
- **No incremental sync / no `syncToken`** — full download each poll.
- **Full re-fetch cost** and latency for large calendars.
- **Data fidelity gaps** — iCal output may not carry every Google-specific field (e.g. some
  reminders, conference data, colors/labels, certain visibility nuances) and may omit declined
  events.
- **No revocation granularity** beyond "Reset" (which breaks all subscribers).
- **The URL is a secret** — store encrypted, never log it.

Good fit for a read-only calendar tool or a low-frequency mirror.

## 3. Google CalDAV — **OAuth2 is mandatory, so this is not an escape hatch**

The current [CalDAV API Developer's Guide](https://developers.google.com/workspace/calendar/caldav/v2/guide)
states plainly:

> The connection must be made over HTTPS and **must use the OAuth 2.0 authentication scheme**.
> The CalDAV server refuses to authenticate a request unless it arrives over HTTPS with OAuth 2.0
> authentication of a Google Account. **Attempting to connect over HTTP or using Basic
> Authentication results in an HTTP `401 Unauthorized`.**

Google's 2023–2024 shutdown of "less secure apps" ended password-based (Basic) auth for
CalDAV/CardDAV/IMAP/SMTP/POP; from **September 30, 2024** password-based CalDAV/CardDAV (including
MDM-pushed configs) stopped working
([Workspace Updates](https://workspaceupdates.googleblog.com/2023/09/winding-down-google-sync-and-less-secure-apps-support.html);
[Transition from less secure apps to OAuth](https://knowledge.workspace.google.com/admin/sync/transition-from-less-secure-apps-to-oauth)).
App passwords were a legacy IMAP/SMTP affordance; they do **not** enable CalDAV Basic auth — Google
rejects Basic outright.

**Conclusion:** CalDAV gives MyOGChat nothing over the REST API. It still requires a user OAuth
client and consent, and therefore inherits the same Testing-mode 7-day refresh-token problem. The
new endpoint is `https://apidata.googleusercontent.com/caldav/v2/CALENDAR_ID/events` (the old
`www.google.com/calendar/dav` endpoint is deprecated).

## 4. Bridges / self-hosted alternatives

- **Local CalDAV/ICS bridge to Google** (vdirsyncer, caldav-sync tools, "CalDAVconnect"-style
  services): the *Google side* of these still authenticates with user OAuth2. They do **not** avoid
  consent for writes; they only add a hop. Useful for fan-out to devices, not for avoiding OAuth.
- **Self-hosted Radicale / Nextcloud / Baïkal as the primary calendar:** make the owner's primary
  calendar self-hosted (open CalDAV, no OAuth), and pull Google in **read-only** via the secret ICS
  feed. This removes Google from the write path entirely and is the strongest privacy play — but
  the owner then loses native Google Calendar features, and syncing *back* to Google still needs
  OAuth. Two-way Google↔self-hosted sync is exactly where consent becomes unavoidable.
- **Google Apps Script (bonus non-consent route):** a script bound to the owner's Google account,
  deployed as a Web App ("execute as: me", "who has access: anyone/only me"), can read and write the
  owner's own calendar **without any OAuth client or consent screen** — Apps Script's implicit
  authorization handles it, and there are no expiring refresh tokens. MyOGChat would call the Web
  App's `/exec` URL (protected by a shared secret / deployment token). Trade-off: the logic lives in
  Google's cloud (not self-hosted), latency and quota are Google's, and it's a different deployment
  surface. Worth offering as an "I want zero GCP OAuth setup" option.

## 5. Comparison

| Route | Setup burden | Credential | Read | Write (create/update/delete) | Token longevity | Main failure modes |
|---|---|---|---|---|---|---|
| **User OAuth2 (baseline)** | High: OAuth client + consent screen; restricted scope verification; Testing mode limited to 100 test users | Refresh token (+ client secret) | ✓ | ✓ (incl. attendee invites) | **Testing: 7 days**; Production+verified: long-lived | 7-day expiry in Testing; consent revoked; verification rejection; unverified-app cap |
| **Service account + shared calendar** ⭐ | Low–med: GCP project + SA + JSON key; share calendar with SA email | **SA JSON key + `calendarId`** | ✓ | ✓ (non-private), **✗ attendee invites without DWD** | **Indefinite** (key until rotated/revoked) | Key leak/rotation; calendar unshared; API disabled; project deleted; quota; `forbiddenForServiceAccounts` on attendees |
| **Secret ICS URL** ⭐ (read-only) | Very low: copy a URL | **ICS URL** (capability) | ✓ | ✗ | Indefinite until Reset | URL leak (→ Reset breaks all); stale cache; no incremental sync; fidelity gaps |
| **Google CalDAV** | High (same as OAuth) | OAuth2 token | ✓ | ✓ | Same as OAuth | Requires OAuth2; Basic auth → 401; not an escape hatch |
| **Apps Script Web App** | Low–med: write script + deploy | Deployment URL + shared secret | ✓ | ✓ (owner's calendars) | Indefinite | Logic off-box; Google quota; endpoint security; less self-hosted |

### Recommendation

- **Read + write → service account + calendar sharing.** Best balance: no consent screen, no
  verification, no 7-day expiry, full create/update/delete on the shared calendar, implementable
  with Go stdlib. Accept the one real limitation: **no attendee invitations** without DWD (which a
  personal account can't use anyway).
- **Read-only → secret ICS URL.** Zero credentials, zero consent, trivial to implement. Ideal for a
  read-only calendar widget/mirror.
- Offer **Apps Script** as an optional "no-GCP-OAuth" fallback for owners who don't want a service
  account key on their server.
- **User OAuth2 is truly unavoidable only when** you need: per-event attendee invitations (the SA
  can't), Calendar **push notifications** bound to a user channel, `freeBusy` across calendars the
  owner doesn't own, or access to **other people's** calendars without asking them to share. If the
  app ever grows beyond a single owner, user OAuth (with verification, or Internal Workspace user
  type) becomes the correct model.

## 6. Impact on the `calendar_accounts` credential design

The credential is no longer "an OAuth refresh token." Model it as a **discriminated union** keyed by
`kind`, with the whole credential blob encrypted via `internal/secret`:

```
calendar_accounts
  id
  kind            -- 'oauth' | 'service_account' | 'ics'
  calendar_id     -- owner email (primary) or calendar ID; NULL/ignored for 'ics'
  credential      -- encrypted blob (internal/secret), shape depends on kind
  created_at, updated_at, ...
```

| `kind` | `calendar_id` | `credential` (encrypted) | Capabilities |
|---|---|---|---|
| `oauth` | owner email / calendar ID | OAuth **refresh token** (+ client_id/secret, token endpoint) | read + write (incl. attendees) |
| `service_account` | owner email / calendar ID | **Service-account JSON key** (`client_email`, `private_key`, `private_key_id`, `token_uri`) | read + write (non-private; no attendee invites) |
| `ics` | — | **Secret ICS URL** | read-only |

Design notes:

- A single `credential` blob (JSON, then encrypted) keeps the schema stable as kinds are added;
  validate/parse per `kind` on load.
- SA access tokens are **not persisted** — cache the access token in memory only for its ~1 h TTL
  and re-mint from the key on expiry. Only the key blob is stored.
- The ICS URL is a bearer secret; encrypt it and treat it like a password (never log, redact in
  errors).
- Expose capability flags per `kind` (e.g. `can_write`, `can_invite_attendees`) so UI/API code can
  hide write actions for `ics` and warn that `service_account` cannot invite attendees.
- Keep `kind = 'oauth'` in the design even if the default is `service_account` — it's the growth
  path and the fallback for attendee invites.
