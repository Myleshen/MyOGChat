# Feature 3.3 — Calendar: provider & implementation research

Scope: list/create/update/delete events from a connected calendar, exposed as
`calendar_*` tools + a Settings section, for **Google Calendar**, **Apple/iCloud
Calendar**, and **Zoho Calendar** (same trio as the planned IMAP email feature
3.2). Target: MyOGChat's single Go binary, `CGO_ENABLED=0`, pure-Go deps,
Raspberry Pi 4B.

---

## 1. Provider access matrix

| Provider | Protocol(s) | Endpoint | Auth | Personal-app pragmatic choice |
|---|---|---|---|---|
| **Google Calendar** | REST **Calendar API v3** | `https://www.googleapis.com/calendar/v3` | OAuth2 (authorization code + refresh token); scope `calendar.events` or `calendar` | **REST v3 + OAuth2** |
| Google (alt) | CalDAV | `https://apidata.googleusercontent.com/caldav/v2/{calendarId}/events` (`/user` for principal) | **OAuth2 only** — Basic/app-passwords rejected (401) | Not recommended (see §3) |
| **Apple/iCloud** | **CalDAV only** (no REST API) | `https://caldav.icloud.com/` → `.well-known/caldav`; home set lands on partition host `pNN-caldav.icloud.com` | HTTP **Basic**: Apple ID email + **app-specific password** (requires 2FA) | **CalDAV + Basic** |
| **Zoho Calendar** | REST API v1 | `https://calendar.zoho.com/api/v1` | OAuth2 | CalDAV is lower-friction (see below) |
| Zoho (alt) | CalDAV | `https://calendar.zoho.com/.well-known/caldav`; events `…/caldav/{calendarId}/events` (region variants `.eu`, `.in`, `.com.au`) | HTTP **Basic**: Zoho email + password or **app-specific password** (if TFA) | **CalDAV + Basic** |

Key facts (primary sources in §8):
- **Apple has no Calendar REST API** → CalDAV is the only path; app-specific
  password is mandatory for third-party clients since 2017.
- **Google killed Basic-auth CalDAV** (CalDAV/CardDAV/IMAP/SMTP/POP) on
  **2025-03-14**; CalDAV now requires OAuth2, and the old
  `www.google.com/calendar/dav` endpoint is deprecated.
- **Zoho** supports both; CalDAV avoids a second OAuth app registration and
  reuses the Apple code path. Its REST API is well-documented but is a
  *separate* integration (OAuth2, `?eventdata={json}` query-param bodies).

**Net:** the trio splits cleanly into **two auth modes** — OAuth2 (Google) and
Basic/app-password (Apple, Zoho) — both speaking CalDAV. Only Google is better
served by REST than by CalDAV.

## 2. CRUD, recurrence, timezones, reminders

### Common normalized operations
- **List in range**: start/end bound, optionally expand recurring instances.
- **Create / update / delete** by event UID (CalDAV) or event `id` (Google).
- **All-day**: `DATE` value (no time, no TZ) vs `DATE-TIME` with `TZID`.
- **RRULE**: store/emit the raw `RRULE` string; expand only for display.
- **Reminders**: CalDAV `VALARM` components; Google `reminders.overrides`
  (or `useDefault`).

### CalDAV (Apple, Zoho, and Google if chosen)
- One event = one **calendar object resource** (`.ics`), addressable by URL;
  `UID` is stable, `ETag` enables optimistic concurrency.
- **List**: `REPORT` `calendar-query` with `<C:time-range start=… end=…/>` at
  `Depth: 1`. Add `<C:expand start=… end=…/>` to have the **server expand**
  recurring instances (RFC 4791 §7.8.3). If unsupported, expand client-side
  from `RRULE`/`RDATE`/`EXDATE` + `RECURRENCE-ID` overrides.
- **Create**: `PUT` a new `.ics` (server may require `If-None-Match: *`).
- **Update**: `PUT` with `If-Match: <etag>` (412 on conflict → re-fetch).
- **Delete**: `DELETE` with `If-Match: <etag>`.
- **Discovery**: `.well-known/caldav` (301) → `PROPFIND` `current-user-principal`
  → `PROPFIND` `calendar-home-set` → `PROPFIND` Depth:1 for collections.
- **Sync**: RFC 6578 `sync-collection` `REPORT` returns changed hrefs + a
  `sync-token` (not universally supported — fall back to time-range query).
- **Timezone**: iCloud/Zoho return `VTIMEZONE` blocks and `TZID=` params;
  map TZID → IANA name → Go `time.LoadLocation`. `TZID` values are usually
  IANA but can be Windows names or `/freeassociation.sourceforge.net/…`.

### Google Calendar REST v3
- **List**: `GET /calendars/{calendarId}/events?timeMin=RFC3339&timeMax=RFC3339
  &singleEvents=true&orderBy=startTime&maxResults=250`. `singleEvents=true`
  **server-expands** recurrence; `nextPageToken` for pagination.
- **Create**: `POST /calendars/{calendarId}/events` (body: `summary`, `start`,
  `end`, `recurrence:["RRULE:…"]`, `attendees`, `location`, `description`).
- **Update**: `PATCH` (partial) or `PUT` (full) `/events/{eventId}`.
- **Delete**: `DELETE /events/{eventId}`.
- **Sync**: `syncToken` from `nextSyncToken` on the **last** page; deleted
  events come back with `status:"cancelled"`. Cannot combine `syncToken` with
  `orderBy`/`q`/`iCalUID`.
- **Recurring edits**: instances carry `recurringEventId` +
  `originalStartTime`; edit a single instance by its instance `id`, or the
  series via the parent id. `events.instances` lists instances explicitly.
- **Timezone**: `start.dateTime` carries an offset; `start.timeZone` (IANA) is
  required for recurring events. `date` (all-day) instead of `dateTime`.
- **Quirks**: `primary` is the alias for the user's main calendar; `calendarId`
  = email for primary, `…@group.calendar.google.com` for secondary. Times must
  be RFC3339 with offset; ms ignored.

## 3. Which protocol per provider? (decision)

| Provider | Recommendation | Why |
|---|---|---|
| Apple/iCloud | **CalDAV + Basic (app-specific password)** | Only option; low friction, no OAuth app review. |
| Zoho | **CalDAV + Basic (app-specific password)** | Reuses Apple path; no second OAuth registration; REST would duplicate work. |
| Google | **REST Calendar v3 + OAuth2** | Handles recurrence/pagination/sync/timezones far better than Google CalDAV; avoids Google CalDAV's OAuth-only + deprecation baggage. |

Using CalDAV for Google is *technically* possible (OAuth2 bearer token), but
it forces the OAuth plumbing anyway **and** adds Google-specific CalDAV quirks
(calendar-id-in-URL, no clean discovery, API de-emphasis). REST v3 with
`singleEvents=true` gives correct recurrence expansion for free. So: **one
CalDAV backend (Apple+Zoho) + one Google REST backend**, behind a shared
interface. Two backends is the honest cost of "same providers as email".

## 4. Go library recommendation

**Constraint check:** repo rule is "single external dep: `modernc.org/sqlite`",
but precedent exists (`github.com/ledongthuc/pdf` was added for PDF extraction).
Prefer pure-Go, CGO-free, permissively licensed, actively maintained.

| Library | Version / license | Pure Go? | Verdict |
|---|---|---|---|
| `github.com/emersion/go-webdav/caldav` | v0.7.0 (Oct 2025), **MIT** | Yes (deps: go-ical, go-vcard) | **Recommended** for the CalDAV backend |
| `github.com/emersion/go-ical` | latest (Jun 2025), **MIT** | Yes (deps: `teambition/rrule-go`) | **Recommended** — ICS encode/decode + `RecurrenceSet` |
| `github.com/teambition/rrule-go` | v1.8.2, **MIT** | Yes | Pulled in transitively; correct RRULE expansion |
| `google.golang.org/api/calendar/v3` | current, BSD-3 | Yes | **Avoid** — pulls `grpc`, `protobuf`, `cloud.google.com/go/auth`, OpenTelemetry, `golang.org/x/*`: a large dep tree for one API |
| `golang.org/x/oauth2` | current, BSD-3 | Yes | Optional; or hand-roll the token refresh (see below) |
| plain `net/http` + `encoding/xml` + `encoding/json` | stdlib | Yes | For Google REST and OAuth2 |

**Recommended set:**
1. **CalDAV (Apple, Zoho):** `go-webdav/caldav` + `go-ical`. It gives discovery
   (`DiscoverContextURL`, `FindCalendarHomeSet`, `FindCalendars`), `QueryCalendar`
   (calendar-query REPORT), `Get/Put/DeleteCalendarObject` with ETag options.
   Adds 4 transitive modules, all pure Go / MIT.
2. **Google REST v3:** stdlib `net/http` + `encoding/json` only — no
   `google.golang.org/api`. Model only the fields we use.
3. **OAuth2 (Google):** implement the ~40-line auth-code + refresh flow by hand
   with `net/http` (POST `https://oauth2.googleapis.com/token`,
   `grant_type=refresh_token`), or add `golang.org/x/oauth2` if the owner
   prefers a vetted implementation. Hand-rolling keeps the dep count at zero.
   Use **PKCE + `access_type=offline`** to get a refresh token.

> If the owner insists on *zero* new Go deps, the CalDAV client can be
> hand-rolled on `net/http`+`encoding/xml` (PROPFIND/REPORT/PUT/DELETE) and ICS
> parsed by hand — but correct RRULE expansion + `VTIMEZONE` + override handling
> is exactly where hand-rolling gets expensive. Recommend taking go-webdav.

## 5. Proposed normalized model + tool schemas

### Normalized event (internal, provider-agnostic)
```go
type Event struct {
    UID         string   // stable id (CalDAV UID / Google id)
    CalendarID  string   // which calendar/collection
    Title       string
    Description string
    Location    string
    Start       time.Time // in event's own TZ
    End         time.Time
    TimeZone    string    // IANA, e.g. "Europe/London"
    AllDay      bool
    Recurrence  []string  // raw RRULE/RDATE/EXDATE lines ([] for single)
    Attendees   []string  // emails
    Reminders   []Reminder // {Minutes int, Action string}
    ETag        string    // CalDAV concurrency token (empty for Google)
}
```

### Tool schemas (mirror `linkwarden_*` style: `Name/Description/Parameters/Run`)

- **`calendar_list`** — `{ from: string(RFC3339, required), to: string(RFC3339,
  required), query?: string, calendar_id?: string, max?: integer }`
  → returns a compact text list (`start – end  Title @ Location [recurring]`).
- **`calendar_create`** — `{ title (req), start (req, RFC3339 or YYYY-MM-DD for
  all-day), end (req), description?, location?, all_day?, timezone?, attendees?:
  string[], recurrence?: string (RRULE), reminders_minutes?: integer[],
  calendar_id? }` → returns created UID.
- **`calendar_update`** — `{ uid (req), title?, start?, end?, description?,
  location?, all_day?, timezone?, attendees?, recurrence?, reminders_minutes?,
  calendar_id? }` → partial update (PATCH for Google, GET+modify+PUT w/ ETag for
  CalDAV).
- **`calendar_delete`** — `{ uid (req), calendar_id? }`.
- Optional v1.5: **`calendar_calendars`** (list collections) to discover
  `calendar_id`.

Keep the tool surface at 4 (matches the brief) and register them per-request
only when the calling user has a calendar connected — exactly how Linkwarden
tools are gated today (`internal/server/integrations.go`).

## 6. Storage & Settings design

**Per-user credentials** (calendar is personal; server-wide would be wrong).
Mirror the existing `users.api_key_enc` pattern and the global `settings`
key/value table:

- New table (additive migration in `internal/store.migrate()`):
  ```sql
  CREATE TABLE IF NOT EXISTS calendar_accounts (
    id            TEXT PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider      TEXT NOT NULL,      -- google | apple | zoho
    calendar_id   TEXT,               -- default collection / calendarId
    username      TEXT,               -- Apple ID / Zoho email (not secret)
    secret_enc    TEXT,               -- AES-256-GCM: app-password OR {refresh_token,...}
    endpoint      TEXT,               -- discovered CalDAV home (Apple partition host)
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL
  );
  CREATE UNIQUE INDEX IF NOT EXISTS calendar_accounts_user_provider
    ON calendar_accounts(user_id, provider);
  ```
  Store the app-password / refresh token (and optionally client id/secret) with
  `internal/secret.Encrypt(s.encKey, …)`. Never return secrets; expose
  `connected: true` + `username_hint` like `has_key`/`key_hint`.

- **Settings UI** (Settings page, mobile-first, vanilla JS): a **Calendar**
  section with one card per provider:
  - Apple/Zoho: email + app-specific password + (optional) server URL for
    self-hosted CalDAV (Radicale/Nextcloud reuse the same path for free).
  - Google: "Connect" button → OAuth redirect → callback stores refresh token.
    Show "Connected as …" + Disconnect.

- **HTTP endpoints** (admin-free; per-user, scoped by session):
  `GET /api/me/calendar` (status), `PUT /api/me/calendar/{provider}`
  (set creds / save tokens), `DELETE /api/me/calendar/{provider}`,
  `GET /api/calendar/oauth/google/start` + `/callback` (Google only).

- **Tool registration**: in `streamReply`/registry build, look up the user's
  `calendar_accounts`; if present, construct the backend client and add the
  `calendar_*` tools. Same pattern as Linkwarden's per-user config.

## 7. Pitfalls

1. **Timezones** — all-day events are `DATE` (no TZ); timed events need an IANA
   `TZID`/`timeZone`. Never assume UTC. iCloud returns `VTIMEZONE` blocks and
   sometimes Windows-style TZIDs; normalize to IANA and fail soft to UTC.
   DST boundaries: expand RRULEs in the event's own `time.Location`.
2. **Recurring events** — prefer **server-side expansion** (Google
   `singleEvents=true`; CalDAV `<C:expand>`). Client-side fallback must honour
   `EXDATE`, `RDATE`, and `RECURRENCE-ID` overrides. Editing one instance vs the
   whole series is a real UX decision; v1 should edit the whole series only and
   document it.
3. **Google OAuth for a personal app** — Testing-mode refresh tokens expire in
   **7 days**; the fix is to flip the OAuth consent screen to **"In production"
   (publishing status), *not* to complete verification** — for a single-user
   self-hosted app you can stay unverified and ignore the warning. Store
   `refresh_token` (only returned with `access_type=offline` + `prompt=consent`).
   Handle `invalid_grant` → prompt reconnect.
4. **Apple partition host** — the CalDAV home set resolves to a per-account
   `pNN-caldav.icloud.com`; **cache the discovered endpoint** in
   `calendar_accounts.endpoint` so we don't re-discover every call.
5. **ETags / concurrency** — CalDAV `PUT` without `If-Match` can clobber a
   concurrent edit; always GET the current ETag before update; treat 412 as
   retry. Google uses no ETag (last-write-wins).
6. **ICS edge cases** — line folding at 75 octets, CRLF, escaped `\,`/`\n` in
   TEXT, `DURATION` vs `DTEND`, missing `DTEND` for all-day, UTF-8, and
   non-standard `X-` properties. go-ical handles most; test against real
   iCloud/Zoho exports.
7. **Pagination / limits** — Google caps at 250 events/page (`nextPageToken`);
   bound `timeMax-timeMin` and `max` in `calendar_list` so the Pi never pulls a
   whole year. CalDAV servers may cap instances (`CALDAV:max-instances`).
8. **Reminders** — CalDAV `VALARM` `TRIGGER` can be `DURATION` (relative) or
   absolute; Google `reminders.overrides` uses minutes. Normalize to
   `{minutes, action}`; don't over-model.
9. **Scope creep to write tools** — create/update/delete mutate real calendars.
   Gate behind the user having explicitly connected an account; consider a
   per-user "allow writes" toggle (default on for a personal app).

## 8. Effort estimate

| Workstream | Effort |
|---|---|
| Store migration + encrypted per-user creds + endpoints | 0.5–1 day |
| CalDAV backend (go-webdav): discovery, list, CRUD, ETag | 1–1.5 days |
| Google REST backend + OAuth2 flow/token store | 1–1.5 days |
| Normalized model + 4 `calendar_*` tools + registry wiring | 0.5–1 day |
| Settings UI (3 provider cards + Google OAuth callback) | 0.5–1 day |
| Tests (ICS fixtures, RRULE, TZ, store) + docs (`docs/3.3-calendar.md`) | 1 day |
| **Total** | **≈ 4–6 focused days** (medium, as scoped) |

Risk multiplier: hand-rolling CalDAV/ICS instead of using go-webdav adds
~1.5–2 days and bug surface.

## 9. Recommendation

1. **Ship CalDAV (Apple + Zoho) first** with `emersion/go-webdav` + `go-ical`
   (MIT, pure Go, CGO-free) and Basic/app-specific-password auth. This is
   self-contained, needs no OAuth app, and — bonus — works for self-hosted
   Radicale/Nextcloud by pointing at a custom server URL.
2. **Add Google via REST Calendar v3** (`net/http` + `encoding/json`, hand-rolled
   OAuth2 refresh) rather than `google.golang.org/api` (its grpc/otel/protobuf
   tree is disproportionate for one API) and rather than Google CalDAV.
3. **Per-user encrypted credentials** in a new `calendar_accounts` table using
   `internal/secret`; tools registered per-request only when connected.
4. Follow the Linkwarden precedent (`internal/tools/linkwarden.go` +
   `internal/server/integrations.go` + Settings) so the code shape is familiar.
5. **v1 scope**: `calendar_list/create/update/delete`; server-side recurrence
   expansion; whole-series edits only; no free/busy, no invites/RSVP, no
   attachments. Document the 7-day Google refresh-token caveat and the
   "publish to production, skip verification" fix.

The 4-module go-webdav/go-ical addition is the one deviation from the
"single-dep" rule; it is pure-Go, MIT, maintained, and far cheaper than
hand-rolling CalDAV + RFC 5545 recurrence correctly on a Pi.
