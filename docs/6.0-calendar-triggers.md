# 6.0 — Calendar triggers (proactive conversations)

Status: **shipped** (server + storage + API; no SPA block yet).
Depends on 3.3 (calendar), 5.7 (detached reply jobs), 5.12 (agent mode), 2.11
(quotas) and 6.2 (project memory — deliberately **not** written here).

Citations name a `file:symbol` rather than a line; lines drift every release.

## What it does

Opt-in, per user. When enabled, the server watches the user's **CalDAV**
calendar and, 15 minutes before each event instance starts, opens a new
conversation titled `Calendar: <summary>` containing the rendered prompt, then
runs it as a normal **agent** reply. The chat appears in the sidebar like any
other; nothing is pushed anywhere else.

It is a trigger, not a scheduler of event creation: there is no daily digest,
no notification, no two-way RSVP, and no background job other than the tick.

## Does this event fire?

| Situation | Behaviour |
|---|---|
| Calendar kind | **CalDAV or Google.** An ICS feed is never read by the scheduler: no time filter, no incremental sync, up to a day of lag |
| Which collection | The connected account's stored collection (`calendar_accounts.calendar_id`); the backend skips discovery when the home set is cached |
| Trigger time | `fire_at = start − 15 min` (fixed; `lead_minutes` is reported by the API but not configurable) |
| Firing window | Fire while `fire_at <= now < start` **and** `now − fire_at <= 10 min` |
| Too late | `now >= start`, or more than 10 minutes past `fire_at` → `skipped_late`, once |
| Not due yet | Nothing is written; a later tick fires it |
| Quiet hours | Local clock inside `[quiet_start, quiet_end)` (crossing midnight is handled) → `skipped_quiet`; the window is **not** deferred |
| Quota | The existing daily/monthly quota refuses → `skipped_quota` with the quota's message |
| Agent job busy | The owner already has an agent job running → `skipped_busy`; triggers **never queue** |
| Server draining | `skipped_busy` with "the server was shutting down"; no job may start |
| Agent mode off (admin) | Nothing at all is read or written — a trigger without tools is not the feature |
| All-day / recurring / no-UID events | All-day events have a start, so they fire. Recurring instances fire independently (the start time identifies the instance). An event without a UID never appears |
| Cancelled / declined events | Not detectable: `calendar.Event` has no status or participant-state field, so they fire like any other event |

## One fire, step by step

`internal/server/calendar_triggers.go:runCalendarTriggerEvent`:

1. The event's trigger time is due and inside the grace window.
2. A run row is **inserted first** with status `reserved`. The unique index on
   `(user_id, event_uid, event_start)` is the dedupe key: if a row already
   exists the insert reports "not inserted" and the tick moves on silently. That
   is why a second tick, a restart, or a slow provider cannot fire twice.
3. A `skipped_*` outcome (late/quiet/quota) updates that row and stops.
4. Otherwise a conversation UUID is generated and the conversation is inserted
   with `AgentMode = true`, the trigger's model and project, title
   `Calendar: <summary>`. A project deleted since the config was saved is skipped
   (the chat is filed as unfiled) instead of failing every tick on its foreign
   key.
5. The rendered prompt is written as the **user message before the job starts**,
   so a triggered chat is never empty (Regenerate works even if the reply
   fails).
6. `startAgentExclusive` (`internal/server/jobs.go`) starts the agent job,
   refusing instead of queueing when the user already has one (`errAgentBusy`)
   or the hub is draining (`errShuttingDown`) — both become `skipped_busy`.
7. The run row flips to `fired` with the conversation id. The job runs detached,
   exactly like a typed agent reply: SSE for a client that opens it, the
   generation snapshot for reattach, a partial reply persisted on stop.

## Dedupe and run statuses

| Status | Meaning |
|---|---|
| `fired` | A conversation was created (and its job started) |
| `skipped_late` | The event already started, or the trigger window passed |
| `skipped_quiet` | Fired inside the configured quiet hours |
| `skipped_quota` | A quota refused the reply; `reason` carries the message |
| `skipped_busy` | The owner's agent slot was taken, or the server was shutting down |
| `failed` | The conversation/user message could not be written |
| `reserved` | Transient: between the dedupe insert and the outcome write within one tick |

A crash between the reservation and the outcome leaves `reserved` for that event
instance, which (correctly) prevents a duplicate fire but means that one
instance is not retried. There is no recovery sweep: a stale reservation is one
missed prep, not a loop.

An event **moved after it already fired** gets a new start time, hence a new key,
hence a second conversation. Keying on the UID alone would fix that but would
lose per-instance firing for recurring events, so the duplicate is accepted.

Every row carries `summary`, `event_start`, `reason` and `created_at`; the
"recent triggers" read is newest-first, capped at 50.

## Timing and cost

- One ticker, **120 seconds**, started from `main.go` after the HTTP server:
  `go srv.RunCalendarTriggers(ctx)`. The loop is serial, so ticks cannot overlap;
  a slow tick makes the ticker drop its slot, and the 10-minute grace absorbs it.
- One `List` per enabled CalDAV account per tick, covering `[now, now + 2 h 15 m]`.
  A cached home set means a CalDAV tick costs **one REPORT**.
- The conversation shares the normal agent budget: 60 minutes wall clock, 60 tool
  rounds, 10 minutes per upstream/tool call.
- Cost is whatever the reply costs; nothing is pre-paid. The agent job may make
  many upstream calls, so the **existing quota** is the hard stop — enable one if
  the calendar is shared with other people.

## Exceptions for triggered replies

A triggered reply is sandboxed differently from a typed one
(`internal/server/chat.go:runReply`, driven by `replySpec.triggered`):

| Exception | Why |
|---|---|
| No `list_chats` / `read_chat` tools | The event text is third-party data; a prompt injection must not be able to browse the owner's other chats. Every other tool stays available, including the persistent workspace |
| No project-memory update | A trigger's prompt is event data, not the owner's own turn; a project chat stays a valid target, but it must not absorb event text into long-lived memory |

What a triggered reply still reads is unchanged: the owner's global memory (6.8,
"about me" context, there is no risk in showing the owner their own note) and the
target project's instructions and memory are injected exactly as for a typed
message. Only chat browsing and memory **writes** are cut off.

Section 5.1's drain guard applies: `jobHub.startLocked` refuses once
`ShutdownJobs` has begun, so a tick that was already reading the calendar cannot
start a reply during shutdown. `ShutdownJobs` then cancels the triggered job like
any other, and an agent partial is persisted.

## Prompt template

Placeholders, replaced from the event; anything else is left exactly as written
(so `{{anything}}` is harmless):

| Token | Value |
|---|---|
| `{{summary}}` | Event title |
| `{{start}}` `{{end}}` | Start / end as RFC 3339 in the server's local time |
| `{{location}}` | Event location |
| `{{description}}` | Event description |

An empty template uses the built-in default (`triggerDefaultPrompt`), which
prepares the owner for the event and states plainly that the details are
untrusted calendar data.

## API

Owner-scoped, no admin variants; the contract is `API_CONTRACT.md` §23.

| Method | Path | Result |
|---|---|---|
| `GET` | `/api/me/calendar/trigger` | Config with defaults, `connected`, `last_error` |
| `PUT` | `/api/me/calendar/trigger` | Any subset (`enabled` alone is valid); `400` on an unknown model/project, malformed quiet hours, one-sided quiet bounds, or enabling without a CalDAV/Google account |
| `DELETE` | `/api/me/calendar/trigger` | `204`, idempotent; removes the config **and** its runs |
| `GET` | `/api/me/calendar/trigger/runs?limit=20` | Newest first, limit clamped 1..50 |
| `POST` | `/api/me/calendar/trigger/preview` | Renders the prompt for the next matching events without writing anything; `502` when the calendar cannot be read |

Quiet hours are strict `HH:MM` local clock times, both set or both cleared.
`last_error` is the last calendar-read error seen by the scheduler in this
process (it resets on restart); a failing fetch logs one `WARN` per user per
10 minutes and records no run row, so the next tick retries.

## Storage

`internal/store/store.go:calendarTriggersSchema`, applied both to a fresh
database and by `migrate()`:

```sql
CREATE TABLE calendar_triggers (            -- one row per user
  user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  enabled INTEGER NOT NULL DEFAULT 0,
  project_id TEXT,
  model TEXT NOT NULL,
  prompt_template TEXT NOT NULL,
  quiet_start TEXT, quiet_end TEXT,         -- "HH:MM" local, optional
  updated_at INTEGER NOT NULL
);
CREATE TABLE trigger_runs (                 -- the dedupe ledger + history
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  conversation_id TEXT,
  event_uid TEXT NOT NULL,
  event_start INTEGER NOT NULL,
  summary TEXT NOT NULL,
  status TEXT NOT NULL,
  reason TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX idx_trigger_runs_dedupe ON trigger_runs(user_id, event_uid, event_start);
CREATE INDEX idx_trigger_runs_user ON trigger_runs(user_id, created_at DESC);
```

Run rows are pruned by the retention janitor after **90 days**. Triggered
conversations are ordinary rows and follow `MYOGCHAT_RETENTION_DAYS` (default 30,
max 60) — a triggered chat is not more precious than a typed one, and the run row
keeps only a pointer to it.

## Privacy — say it plainly

Enabling this makes the server **read your calendar by itself**, on a timer, and
send event text to the model you chose. Specifically:

- The scheduler decrypts your calendar credential in-process (the same path the
  calendar tools use) and issues one read per tick.
- Whatever the trigger fires for, the event's summary, start, end, location and
  description are placed in a normal chat message. That message is stored in the
  app's database, follows the retention window, and is sent upstream to the
  model — which may be a third-party provider you configured. The model's reply
  is stored the same way.
- **Anyone who can put an event on your calendar can put text in front of the
  model**, including text that looks like instructions. That is why the default
  template labels the event as untrusted data, why triggered replies cannot read
  your other chats, and why enabling quotas is recommended.
- Disconnecting the calendar stops triggers (no credential, no read); the config
  row is kept so reconnecting resumes. Deleting the trigger removes the config
  and the whole run ledger.

## What is not verified

- No real iCloud/Zoho account was exercised: the tests drive a fake CalDAV
  server. Real-server recurrence expansion, UID stability across refreshes, and
  how often a provider lags are unmeasured.
- There is no SPA block for the trigger yet (config is API-only); the Settings UI
  described in the original design is not built.
- No daily cap and no per-trigger timezone: quiet hours use the server's local
  clock, and the guard against runaway spend is the existing quota.
