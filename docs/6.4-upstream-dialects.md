# 6.4 — Upstream dialects

Status: **implemented and unit-tested; authenticated calls not exercised, so live behaviour is unproven.**
**Guiding principle: simple, fast, snappy, minimal resources.**

Four wire protocols reach the OpenCode Go gateway. Each adapter lives in
`internal/upstream` and normalizes its stream into one `Event` channel
(`reasoning`, `text`, `usage`, `error`) plus a `ToolCall` per requested tool, so
the server, the SPA and the agent loop do not know which dialect answered.

| dialect | adapter | endpoint | catalog models |
|---|---|---|---|
| `chat` | `streamChat` / `agentChat` | `POST .../openai/v1/chat/completions` | most of the registry |
| `responses` | `streamResponses` / `agentResponses` | `POST .../openai/v1/responses` | GPT 6/5.6 Luna, Grok 4.7 |
| `anthropic` | `streamAnthropic` / `agentAnthropic` | `POST .../anthropic/v1/messages` | Claude Haiku 5.5, MiniMax M3, Qwen3.7 Plus, Qwen3.8 Flash/Max, Qwen4 Max |
| `google` | `streamGoogle` / `agentGoogle` | `POST .../google/v1beta/models/{model}:streamGenerateContent?alt=sse` | Gemini 4 Argon |

`Params.Dialect` picks the adapter; `models.Registry` decides it per model from
the catalog's `recommended_api` (`TestRegistryMatchesCatalog` fails on drift).

## What each adapter maps

### Chat completions (unchanged)

`messages[]` (+ a leading `system` message for attachment context and project
instructions), `stream_options.include_usage`. `delta.reasoning_content` →
reasoning, `delta.content` → text, `usage.prompt_tokens_details.cached_tokens` →
cached. Tools arrive as `tool_calls` deltas; a replayed round becomes an
assistant `tool_calls` message plus one `tool` message per result. No output
budget is sent.

### Responses (unchanged, one fix)

`input[]` with a leading `system` item for context, `instructions` for the
project prompt, `reasoning:{effort, summary:"auto"}`, `store:false`.
`response.output_text.delta` → text, `response.reasoning_summary_text.delta` →
reasoning, `response.completed` → usage and the authoritative function calls.
Now takes the shared turn budget in `max_output_tokens` (was a hard-coded 4096).

### Anthropic Messages

- **Auth/headers**: `x-api-key` and `Authorization: Bearer` (the gateway accepts
  either; both are sent), `anthropic-version: 2023-06-01`,
  `Accept: text/event-stream`, `x-opencode-session`, `User-Agent: myogchat/1.0`.
- **System**: attachment context and project instructions folded into the single
  top-level `system` string, blank-line separated.
- **History**: each message becomes a list of content blocks — `text`, `image`
  (`{"source":{"type":"base64","media_type","data"}}` from a `data:` URI), and
  for a stored tool round the assistant's `tool_use` blocks followed by a **user**
  turn of `tool_result` blocks. Messages requires the results in the very next
  user turn, which is why the replay builds that pair itself.
- **Tools**: flat `{name, description, input_schema}`; the streamed `input_json`
  deltas are accumulated per content-block index.
- **Stream**: `message_start` (input and cache-read usage), `content_block_start`
  (first text/thinking chunk, `tool_use` id+name), `content_block_delta`
  (`text_delta`, `thinking_delta`, `input_json_delta`), `message_delta`
  (cumulative output tokens), `message_stop`, `error`; `ping` ignored.
- **Budget**: `max_tokens` is required — the request is invalid without it, so
  the server's `turnMaxTokens` (8192) is always sent; a direct caller that sets
  none falls back to `defaultMaxTokens` (4096).

### Google generate-content

- **Auth/headers**: `Authorization: Bearer` (the gateway also accepts
  `x-goog-api-key`), `x-opencode-session`, `User-Agent: myogchat/1.0`.
- **System**: attachment context and project instructions as
  `systemInstruction.parts[]`.
- **History**: `contents[]` with roles `user` / `model`. Assistant text, inline
  images (`inlineData` with raw base64) and `functionCall` parts; each stored
  tool round also appends a following `user` turn of `functionResponse` parts
  (`{name, response:{result}}`). Google matches responses **by name**, so call
  ids are synthesized locally (`google_<iter>_<n>`).
- **Tools**: one `functionDeclarations` array; the schema passes through.
- **Thought signatures**: `parts[].thoughtSignature` is captured with each
  `functionCall` (including a signature delivered in a part of its own right
  after the call) and echoed back on that same part in the next loop request.
  It is persisted in `messages.tools[].thought_signature` and replayed on the
  call in later turns, so a reloaded conversation can still use tools. Gemini
  rejects a tool turn whose `functionCall` part lost its signature
  (`INVALID_ARGUMENT: Function call is missing a thought_signature …`). A call
  that arrives without a signature is replayed without one — nothing is
  invented.
- **Config**: `generationConfig.maxOutputTokens` (the shared turn budget),
  `temperature: 1.0`, and `thinkingConfig.includeThoughts: true` plus a
  `thinkingBudget` derived from the effort control (`none` 0, `low` 1024,
  `medium` 8192, `high` 24576, `xhigh`/`max` −1 meaning dynamic, empty = omit).
- **Stream**: accepts SSE `data:` objects or a chunked JSON array, because
  `alt=sse` is not guaranteed. `parts[].text` → text, `parts[].thought:true` →
  reasoning, `parts[].functionCall` → a tool call, `usageMetadata` →
  prompt/cached tokens with `candidatesTokenCount + thoughtsTokenCount` as the
  billed completion count. A truncated tail ends the reply cleanly instead of
  failing it.

## Event-model gaps (what a dialect cannot carry)

The normalized `Event`/`Usage` shape predates these two adapters, so some wire
detail is deliberately dropped. None of it is needed to render a reply, but it
is missing from cost/debug surfaces:

**Anthropic**

- `cache_creation_input_tokens` — cache *writes* are billed at a higher rate and
  are not counted anywhere. `Usage` has one cached-token field (cache reads).
  Cost is therefore under-reported on the first turn of a cached prefix.
- Thinking-token count — Messages reports `output_tokens` only, with no
  thinking breakdown, so `reasoning_tokens` stays 0 and the thinking block's
  token count is absent.
- `signature_delta` and `redacted_thinking` — signed/redacted reasoning blocks
  are ignored. They must be echoed back on the next turn for strict multi-turn
  thinking continuity; the adapter never sends them, which is fine today
  because it never requests thinking.
- `stop_reason` (`max_tokens`, `tool_use`, …) is not surfaced; the UI infers
  nothing from it.

**Google**

- `finishReason` / `promptFeedback.blockReason` — not surfaced; a safety block
  looks like an empty reply, and a truncated or blocked reply has no
  `finishReason` event the adapter can act on (the stream just ends cleanly).
- Grounding metadata (`groundingMetadata`, citations) — dropped.
- Parallel-call ids — Google returns no ids; synthesized ids are stable per
  iteration only, and two same-name calls in one turn are distinguished by
  order, not by id.
- Audio input (the catalog prices it separately) is not sent; only text and
  `image/*` inline data.

## Residual risk: gateway-shaped guesses

These are guesses at the gateway's shape, not authenticated round-trips:

- The Google base (`.../inference/go/google/v1beta`), the `:streamGenerateContent`
  path and `alt=sse` were taken from contract §4, not from a live 200.
- `generationConfig.temperature: 1.0` is the Gateway's default mirror, not a
  measured value; there is no per-model user control for it.
- `thinkingConfig.thinkingBudget` values (1024 / 8192 / 24576 / −1) are our
  mapping of our effort names onto Gemini's range; if the gateway rejects a
  value every effort-driven Google call fails. The same applies to
  `maxOutputTokens`, though it is at least a plain cap.
- The Anthropic `anthropic-version` header value and the dual auth headers were
  probed anonymously (a 401 says the shape was understood, not that it works).
- No Go test in this repo makes an authenticated call. Unit tests use `httptest`
  servers that replay hand-written frames copied from the vendor docs, so they
  prove our parsing, not theirs. The `thoughtSignature` capture/echo is covered
  that way only; whether the gateway accepts our echoed part verbatim is still
  unproven against a live key.

## Agent loop

Both adapters run the same loop the other two use: up to
`AgentOptions.MaxIterations` rounds, tools offered on every round but the last
(so the model must answer), one tool retry without tools if the model rejects
them on round 0, per-round call timeout, `OnStep` progress, usage summed across
rounds, and the streamed assistant text replayed as the `tool_use` /
`functionCall` turn. Tests: `TestAnthropicToolUseLoop`,
`TestStreamAgentGoogleToolLoop`, plus `TestDialectTurnBudget` for the budget on
the wire.
