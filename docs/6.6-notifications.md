# 6.6 — Web Push notifications

Status: **server shipped** (`internal/push`, `internal/server/push.go`); the
Settings UI is a separate pass, so the endpoints below are what the SPA calls.
**Guiding principle: simple, fast, snappy, minimal resources.**

A reply that finishes while you are not looking should reach your phone even
with the PWA closed. The server sends a Web Push message to the browser's own
push endpoint — no third-party push service, no new dependency: VAPID (RFC 8292)
and `aes128gcm` payload encryption (RFC 8291) are implemented on the standard
library (`crypto/ecdh`, `crypto/hkdf`, `crypto/ecdsa`, `crypto/aes`).

## What a notification says — and never says

| | |
|---|---|
| Title | the conversation title (`New chat` when it has none yet) |
| Body | `Reply ready`, `Job failed`, or `Job stopped` |
| URL | `/#/c/<conversation id>` — focused, or opened in a new tab |
| Tag | the conversation id, so a newer notification replaces an older one |

The payload is **never** message content, a prompt, a project name, a model
reply or usage numbers. A notification sits on a lock screen, and the push
service relays it: end-to-end encryption protects it from the service, but not
from whoever can see the phone. Payloads are JSON (`{title,body,url,tag}`),
encrypted and capped at 3993 bytes (RFC 8291 §4), so the limit is not reachable
by this shape.

## When a send happens

A notification is queued only when **no live SSE client is watching the reply**
at the moment the job reaches a terminal state — reading a chat on any device
never buzzes the phone. Three terminal states notify:

- `done` — the reply was persisted.
- `error` — only when the job left a partial reply (agent mode). A normal chat's
  failure persists nothing, so there is nothing to open.
- `stopped` — only when a stopped agent job persisted a partial.

Calendar-triggered replies notify like any other. Sends run in a goroutine with a
10 s timeout, at most four in flight; when all four are busy the notification is
dropped rather than queued. A failure is logged at Debug and can never affect
the reply or the job.

## Delivery and pruning

| Push service answer | What happens |
|---|---|
| 2xx | `last_used` moves, the failure streak resets |
| 404 / 410 | the subscription row is deleted (the browser forgot it) |
| anything else | the streak increments; 5 consecutive failures delete the row |

The admin setting **`push_enabled`** (default on) gates every send and returns
`503` from the test endpoint. It does not delete anybody's subscriptions.

## Subscriptions

One row per browser subscription, **keyed by endpoint** (unique index): a
browser that rotates its keys or a different account signing in on the same
device updates the existing row instead of adding another. Every row is owned by
one user; another user's subscription id is a 404. Deleting a user cascades to
their subscriptions.

Each row stores the endpoint, the browser-generated `p256dh` (uncompressed P-256
public key) and `auth` (16-byte secret) plus an informational user-agent string.
Those keys are public halves (they encrypt payloads); the endpoint is a bearer
credential, which is why the API never returns it and only the owner may delete
the row.

## VAPID key pair

Generated once, on first use, and stored as an encrypted PKCS#8 key in the
`settings` table (`vapid_private_key`, AES-256-GCM under the server's key
encryption key). The public key is derived, returned by
`GET /api/me/notifications` and used as `applicationServerKey` when subscribing.
Neither key is ever logged. Deleting the row rotates the pair — every existing
subscription then fails with 403 and is dropped after five attempts, so the
devices must subscribe again.

## Browser support

Web Push needs a **secure context** (HTTPS or localhost) and a service worker:
Chrome/Edge on Android and desktop, Firefox, and Safari 16.4+ (iOS/iPadOS too —
install the PWA to the home screen or notifications are refused). Private
browsing cannot receive them. `GET /api/me/notifications` reports `supported`
(the server has a VAPID key) and the caller's `subscriptions` count; the browser
side is the usual `Notification.permission` → `pushManager.subscribe`.

## Removing a device

Two ways:

- In the app, delete the subscription (the SPA lists them by user-agent string;
  `DELETE /api/me/push/{id}`).
- In the browser, site settings → Notifications → Block, or uninstall the PWA.
  The next send gets 404/410 and the row is pruned automatically.

## Limits and caveats

- Jobs are in memory (5.7): a server restart mid-reply sends nothing.
- A notification arrives at most once per finished job; there is no retry, so a
  push service outage loses it (the reply itself is still there).
- The Pi keeps one goroutine per in-flight delivery, capped at four.
