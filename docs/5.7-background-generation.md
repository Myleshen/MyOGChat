# 5.7 — Background / concurrent generation

Status: researched, **planned** (not implemented). Design of record.
**Guiding principle: simple, fast, snappy, minimal resources.**

## Problem

One reply at a time freezes the whole app: `state.streaming` / `state.abort` are
single globals, so while chat A streams you cannot start or read another chat,
and navigating away leaves the live bubble detached (the reply *is* persisted but
the client early-returns and shows nothing).

The server is **not** the limit — `net/http` already runs each request in its own
goroutine and every per-request structure is local. The fix is entirely in the
SPA.

## Recommended design (client-side only, no server/API/schema change)

Replace the `state.streaming` / `state.abort` singletons with a small
**per-conversation map** `state.streams = Map<convId, {controller, ui}>`.

- Navigation never aborts a stream. A stream writes to the DOM **only when its
  conversation is visible** (`stream.convId === state.current.id`); returning to
  it re-renders the live bubble from the in-memory `ui`.
- Fix the latent bug where the `done`/auto-title handler uses `state.current`
  instead of the stream's `convId` (wrong title on switch).
- Per-conversation **Stop** (composer + row menu). A small spinner on the sidebar
  row is enough — no global job hub.
- Files: `static/app.js`, `static/style.css` (tiny), `static/index.html` (badge
  optional).

That is the whole feature: start in A, switch to B, come back to A's finished
reply — within the session. No new endpoints, no schema, no background
machinery, nothing extra on the Pi.

## Explicitly out of scope (only if later needed)

Reload/tab-close resilience would require **server-detached jobs** (a job hub, a
snapshot endpoint, SSE resume). That is more moving parts, more memory, and a
deliberate contract change (today the upstream call is aborted on disconnect).
Do it **only if** the user asks for "survives reload" — otherwise the existing
Retry affordance covers an interrupted reply.

## Decisions (minimal)

1. Per-conversation Stop placement: composer button for the visible chat + a Stop
   item in the row "…" menu. (No global queue UI.)
2. On background completion, a one-line toast "Reply ready in <title>" — cheap and
   helpful; skip if noisy.

## Risks

- Nothing new on the server; the only risk is SPA state bugs. Cover with the UI
  battery (start two chats, switch, both complete).
- LAN HTTP/1.1 6-connection cap: a handful of concurrent streams is fine; no
  action needed for a personal app.
