# 5.7 — Background / concurrent generation

Status: **implemented** (branch `feat/p57-background`). Design of record.
**Guiding principle: simple, fast, snappy, minimal resources.**

## Problem

One reply at a time froze the whole app: `state.streaming` / `state.abort` were
single globals, so while chat A streamed you could not start or read another
chat, and navigating away left the live bubble detached (the reply *was*
persisted but the client early-returned and showed nothing). A reload/tab close
aborted the upstream call entirely.

## Implemented design — server-detached jobs

The user decision: a reply **must survive a reload or tab close**, so the
client-only design was superseded by **server-detached jobs**.

### Server (`internal/server/jobs.go`, `chat.go`, `server.go`)

- A reply runs in a `genJob` owned by the server, not the HTTP request:
  `{id, convID, userID, model, ctx/cancel, status, messageID, title, accumulated
  content/reasoning/tools/usage, subscribers, terminal snapshot}`.
- `jobHub` (keyed by conversation) enforces **one running job per conversation**
  (a second start → `409`) and a small global (8) / per-user (3) cap (`429`).
  A terminal job is kept for a 60 s grace period so a reload can still read it.
- `runReply` owns the agent loop and **all DB writes** (user-message insert /
  trailing-reply delete, `ListMessages`, `InsertMessage`, `TouchConversation`,
  auto-title) on a **detached** `context.Background` (15 min budget) — never
  `r.Context()`. It publishes progress (text/reasoning/tool/usage) to the job.
- `relayJob` subscribes and writes the SSE frames. The **wire format is
  byte-identical** to before. On client disconnect the relay unsubscribes and
  returns; the job keeps running and persists.
- New endpoints (owner-scoped):
  `GET /api/conversations/{id}/generation` (snapshot for reattach/poll) and
  `POST /api/conversations/{id}/generation/stop`.
- `main.go` cancels and drains running jobs on shutdown.

Jobs are **in memory only** — no schema change, nothing extra stored.

### SPA (`static/app.js`)

- `state.streaming` / `state.abort` are replaced by a per-conversation
  `state.gens` map. Navigation **never** aborts; a stream renders only when its
  conversation is visible and is re-rendered from its buffers on return.
- On opening a conversation the SPA probes the generation snapshot: a running
  reply (started here, on another device, or before a reload) is rehydrated and
  polled until it finishes.
- Fixed the latent bug where `done`/auto-title used `state.current` instead of
  the reply's own conversation id.
- Per-conversation **Stop** (composer + row menu), a sidebar spinner and an
  “N generating” chip, and a one-line toast when a background reply completes.

## Out of scope

- Resumable token-level SSE after a reload: the reattach path **polls** the
  snapshot (~1 s) rather than resuming the byte stream. Simple and sufficient.

## Risks

- The only meaningful risk is SPA state; covered by the Go tests
  (`internal/server/jobs_test.go`) plus the UI battery.
- LAN HTTP/1.1 6-connection cap: a handful of concurrent streams is fine.
