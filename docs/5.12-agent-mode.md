# 5.12 — Agent mode

Status: **shipped in v0.1.0 and verified live** (queue, persistent workspaces,
owned files, Docker toolbelt, stop-with-partial).
**Guiding principle: simple, fast, snappy, minimal resources.**

## Problem

A normal chat is one turn: at most a handful of tool rounds, a 15-minute reply
budget and a `/work` directory that is deleted after every `run_bash` /
`run_python` call. A task that needs dozens of steps — clone, build, test,
fix — cannot keep its files between calls, and one turn cannot run for an hour.

## What it is

A per-conversation opt-in flag (`conversations.agent_mode`, additive migration).
An agent-mode conversation keeps everything a normal chat has, plus:

- a bigger budget (60 minutes, 60 tool rounds, 10 minutes per upstream or tool
  call) and a per-user scheduling queue;
- a **persistent** sandbox workspace, bind-mounted at `/work` and kept between
  calls, quota'd per user;
- partial-reply persistence on Stop, graceful shutdown and failure.

**Ordinary chats are untouched**: they keep the ephemeral sandbox, the 15-minute
job budget and the existing 409-on-second-send behaviour. The flag is per
conversation and can be flipped at any time; it decides how the *next* send runs.

## Opting in

`PATCH /api/conversations/{id} {"agent_mode":true|false}`, or
`POST /api/conversations {"agent_mode":true}`. The flag is returned on every
conversation object, so the SPA can render the toggle from `GET
/api/conversations` (contract §3.8).

## Budgets and scheduling

| Limit | Value | Where |
|---|---|---|
| Whole job (wall clock, tools included) | 60 min | `agentJobTimeout` |
| Tool rounds | 60 | `agentMaxSteps` |
| One upstream call | 10 min | `agentCallTimeout` |
| One tool call | 10 min | `agentToolTimeout` |

Scheduling is **one agent job per user at a time** (for sends), across all of
that user's conversations:

- User idle → the send starts immediately and streams SSE as usual (`200`).
- User already running an agent job → the send joins a server-side **FIFO
  queue** and the request returns `202 {"queued":true,"position":N}`. The user
  message is stored before the response is written, so it is visible in the chat
  straight away.
  No API key is held while queued; it is resolved when the job starts.
- Second send in the **same** conversation while it is running or queued →
  `409` (nothing is stored).
- When a job finishes, the next queued send starts on its own.
- The process-wide (8) and per-user (3) detached-reply caps still apply: a send
  that cannot start because they are full gets `429`. A queued send that cannot
  start stays at the head of the queue.

Regenerate in an agent conversation also runs as an agent job (same budget, same
workspace), but it is not queued: it starts or returns `409`/`429`.

## Persistent workspace

Host path: `~/.local/share/myogchat/sandbox/agent/<userID>/<convID>` — one
directory per conversation, mounted rw at `/work` for each `run_bash` /
`run_python` call and **never removed by the call**. That is the only difference
from an ordinary sandbox call: the container itself is still fresh each time,
read-only apart from `/work`, non-root, capability-free and network-limited
exactly as in `docs/2.6-2.7-sandbox.md`. `/tmp` stays an ephemeral tmpfs.

Sizes and lifetime:

- **5 GiB per user** by default, measured over the whole
  `agent/<userID>` tree (all conversations together). `MYOGCHAT_AGENT_QUOTA_BYTES`
  overrides it; `0` disables the check. When the tree is at or over the limit a
  tool call is refused before anything runs with a clear
  `ErrQuotaExceeded`-derived message telling the model to delete files in `/work`
  or remove an old workspace.
- The quota is measured by walking the tree, cached for **60 s** — a long run
  would otherwise re-walk gigabytes on every tool call.
- The per-file `fsize` ulimit is raised for agent runs (2 GiB per file,
  `2147483648:2147483648`, instead of 10 MiB), so a single file is not clipped
  at 10 MB; the total is bounded by the quota. Docker's `--ulimit` parser takes
  plain bytes only, so the value must never carry a `2g`-style suffix.
- An **hourly** janitor sweep removes conversation workspaces whose directory
  mtime is older than **7 days**, then any empty user directory left behind.
  Deleting the conversation also removes its workspace directory (best-effort:
  a failure is logged, and the row is already gone, so the sweep is the backstop).
- Users can see and reclaim space without shell access: `GET
  /api/me/agent/workspaces` lists the existing workspaces (conversation, title,
  bytes, last-modified) and `DELETE /api/conversations/{id}/workspace` removes
  one (idempotent `204`). Both are in Settings.

## Disk guard

Before an agent send is accepted the server checks the sandbox filesystem and
refuses with `507 {"error":"not enough disk space on the server to start an
agent workspace"}` when it has under **1 GiB** free. An unreadable path fails
open (the send proceeds) — the check must never be the reason a chat stops
working.

## Artifacts

The 5.8 harvest still runs after every sandbox call, but restricted to files
modified at or after the call started, so a persistent workspace does not
re-attach everything it already produced. Identical content in the same
conversation returns the **existing** artifact (SHA-256 per conversation)
instead of storing another copy. The caps are unchanged: 10 MB per file, 25 MB
total, 20 files per call. A file over 10 MB stays in `/work` but is not
attached.

## Stop and failure

- Stopping a **running** agent job cancels it and **persists the partial reply**
  (content, reasoning, tool activity, images, artifacts; no usage, since the
  stream never reported it). An empty reply is not stored. A long run is
  expensive, so the partial answer is kept — unlike a normal chat, where a
  stopped reply is discarded.
- A job that **fails** persists the same partial row before the client gets its
  `error` frame: an upstream error, a stream that closes without usage (which is
  how a per-call timeout surfaces), or the 60-minute job budget running out. The
  row is an ordinary assistant message with what the run produced so far; it
  records no usage and carries no "success" marker, and the snapshot still
  reports `status:"error"` with the real message. A run that produced no text and
  no reasoning stores nothing. A **normal chat** keeps the old behaviour: a failed
  reply is discarded.
- Every terminal job failure is logged at `WARN` with the conversation id, the
  agent flag, elapsed time and the error — one line per failed job.
- Stopping a **queued** send removes it from the queue and returns `204`.
- `404` when there is nothing to stop.

## Generation snapshot

`GET /api/conversations/{id}/generation` gains two things for agent jobs:
`status` also reports `queued`, and an `agent` block:

```json
{"enabled":true,"step":3,"max_steps":60,"queued":false,"queue_position":0}
```

`step` is the current 1-based tool round; a queued send has
`step:0, queued:true, queue_position:N`. The `agent` block is absent for a
normal chat. The SPA polls the snapshot while the SSE stream is attached so the
composer can show progress ("step 3/60") and a queued send's position.

## Admin kill switch

`agent_enabled` (default **on**) is an admin setting
(`GET`/`PATCH /api/settings`). When off, an agent-mode conversation behaves
exactly like a normal chat — ephemeral workspace, normal budget, no queue —
nothing is refused or lost; the messages simply reply as usual. The flag is
also exposed to every user on `GET /api/auth/me` so the UI can explain why the
toggle has no effect. Workspaces already on disk can still be listed and
deleted.

## Known limits

- **One agent job per user for sends.** Two long sends for the same user
  serialize; that is the Pi's memory budget talking, not an oversight. A
  regenerate is not queued, so it can run beside one (within the global/per-user
  caps).
- **In memory only.** A restart drops running and queued agent jobs. A queued
  send's user message is already stored; a running job's partial reply is kept on
  an explicit stop, a graceful shutdown, or a terminal failure, which all go
  through the same persistence path.
- **No `GITHUB_TOKEN`.** There is no way to authenticate a clone, so private
  repositories cannot be fetched.
- **Quota is sampled.** The 60 s cache means a burst of writes can overshoot the
  quota briefly; the next call refuses.
- No per-user agent limits beyond the quota and the one-job rule.
