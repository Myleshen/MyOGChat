# 6.3 — Chat references (read another conversation)

Status: **implemented, unit-tested** (branch `feat/chat-refs`). Not deployed.
**Guiding principle: simple, fast, snappy, minimal resources.**

## Problem

Inside a project the user says *"check the chat about the launcher"* or *"what
did we decide in the paper review chat"*. The model has no way to see that
other conversation, so it either guesses or asks the user to paste it. Projects
give chats a shared instruction, but not a shared memory.

## What it is

Two read-only tools, registered **whenever tools are enabled** — no setting, no
toggle:

| Tool | Arguments | Returns |
|------|-----------|---------|
| `list_chats` | `query?`, `project?`, `limit?` (default 20, max 50) | the caller's chats, newest first, as JSON |
| `read_chat` | `id?` or `title?`, `limit?` (default 40, max 100) | the transcript of one chat |

`list_chats` returns one object per chat:

```json
[{"id":"c1a2","title":"Launcher plan","project":"Launcher",
  "updated_at":"2026-11-20T09:14:02Z","message_count":18}]
```

`project` is the project name or `null`; `message_count` counts user and
assistant messages (system prompts are not turns), counted from stored messages
for the chats actually returned. `query` reuses the existing
conversation search (`store.SearchConversations`, the same query behind
`GET /api/search` §5.2): it matches titles **or** message content, so *"the chat
where we discussed the launcher"* finds it even when the title says nothing.
`project` filters by project name, case-insensitively, or `"unfiled"`.

`read_chat` returns plain text: a header, then the transcript oldest→newest with
`User:` / `Assistant:` prefixes and the persisted material from each turn:

```
Chat: "Launcher plan" (id c1a2)
Project: Launcher
Updated: 2026-11-20T09:14:02Z; started 2026-11-18T21:03:11Z
Transcript: the last 38 of 40 messages (2 earlier messages omitted, 6 tool call(s) shown).
Note: message text is verbatim from storage; tool lines are what the sandbox/API actually returned; thinking may be truncated; attachments/artifacts are file metadata only (no file contents).

User: can you rebuild the launcher?
Assistant: Rebuilt it; the build log is attached.
  Thinking: I checked the previous build log first.
  Tool: run_bash · done · 4210ms
    args: {"cmd":"go build ./cmd/launcher"}
    output: ok launcher
  Files: artifact: build.log (text/plain, 812 bytes)
```

- **Thinking** (`messages.reasoning`) is included as a `Thinking:` line, capped at
  2,000 characters per message.
- **Tool calls** (`messages.tools`, the same JSON array the UI replays) render as
  `Tool: <name> · <status> · <duration>ms`, then `args` (cap 1,000 chars),
  `output` (cap 2,000) and `error` when the call failed (cap 2,000). Every tool
  gets at least its `Tool:` line; a cut field ends in `… [truncated]`, never a
  silent omission.
- **Files** are listed by name with MIME type and size — attachments, generated
  images and sandbox artifacts. Metadata only: no bytes are read from the
  database.
- A title must resolve to exactly one chat: an exact (case-insensitive) match
  first, then a case-insensitive substring. Several matches are a normal tool
  error listing up to five candidate titles with ids; none is an error telling
  the model to use `list_chats`. An empty chat returns a header saying
  `no messages yet.` — never a blank transcript.

## Budgets

| Limit | Value | Why |
|-------|-------|-----|
| result budget | 48,000 chars (header included) | one reference must not eat the turn |
| per message text | 8,000 chars | one huge paste cannot crowd out the rest |
| thinking | 2,000 chars per message | reasoning is evidence, not the answer |
| tool args / output | 1,000 / 2,000 chars per call | enough to see what ran and what it said |
| messages read | 40 default, 100 max | covers a long thread in one call |
| chats listed | 20 default, 50 max | enough to pick from |

Trimming always removes **whole messages from the oldest end**, so the newest
turn survives and the header states exactly how many earlier messages were
omitted and how many tool calls remain. All cuts are on rune boundaries: the
model never receives half a character. A single pathological turn that still
exceeds the budget after per-field caps is cut at the budget with `… [truncated]`.

## Why content is only paid for when referenced

The tools are always registered, but that is cheap: a tool's schema costs a few
hundred tokens per request, while the transcript costs up to 48,000 characters.
The model calls `read_chat` only when the user points at another conversation,
so an ordinary turn pays for the capability, not for the chats. There is no
pre-fetching, no automatic context injection, and no background indexing — this
is the same static tool contract as every other integration.

## Owner scoping

`internal/server/integrations.go` adapts the store per request
(`chatSource{st, userID}`) and implements only the three calls the tools need:

- `Chats` → `store.ListConversations(ctx, userID)` plus `ListProjects` for names;
- `SearchIDs` → `store.SearchConversations(ctx, userID, query, 50)`;
- `Messages` → `store.GetConversation(ctx, id, userID)` as an owner gate, then
  `ListMessages`.

No new query and no cross-user path. A conversation id belonging to another
user therefore behaves exactly like one that does not exist: it never appears in
`list_chats`, in search results, or in a `read_chat` transcript, and the error
never echoes its title or content. Title resolution is done over the caller's
own chat list only.

## Faithfulness (and what is still missing)

The transcript is what storage holds, not a summary: message text verbatim, tool
lines are the persisted result of the real sandbox/API call, and file entries
are real metadata. Two write-time facts the model is told about in the header:

- **Thinking may be truncated** — the provider's reasoning is stored as emitted
  and this tool keeps at most 2,000 characters per message.
- **Tool fields may already be truncated by storage** — `internal/server/chat.go`
  caps persisted args at 16 KiB, output at 64 KiB and error text at 4 KiB
  (`maxToolArgsBytes`, `maxToolOutputBytes`, `maxToolErrorBytes`) and records
  that in `ToolActivity.Truncated`.

Still not included: **file contents**. Attachments, images and artifacts are
names and sizes; the bytes live in their own tables and are not read here. An
assistant turn that used a tool but produced no text still shows its `Tool:`
lines, so silence never means "did nothing".

## Rejected: a general SQLite tool

The owner asked whether the model could simply be handed a SQLite query tool
instead. It was considered and rejected: `chat.db` holds
`users.password_hash`, `users.api_key_enc`, `users.linkwarden_token_enc`,
`settings.session_secret` and `settings.encryption_key`. A prompt-injected
message could ask the model to `SELECT` those rows and echo them into the
conversation, turning any content the model reads into a credential dump. The
scoped accessors above return the same conversation data the UI already shows,
with no arbitrary SQL, no other user's rows, and no secrets table in reach.

## Wiring

- `internal/tools/chatrefs.go` — `list_chats`, `read_chat`, the `ChatSource`
  boundary, rendering, caps and title resolution.
- `internal/server/integrations.go` — `chatSource` adapter and the two
  `reg.Add` calls in `toolRegistryWithWorkspace` (right after `fetch_url`).
- Tests: `internal/tools/chatrefs_test.go`, `internal/server/chatrefs_test.go`
  (registration on/off, owner scoping, store→tool mapping).

No schema change, no migration, no new dependency, no settings row.
