# 3.3 — Calendar

Status: implemented on branch `feat/calendar` (worktree `myogchat-wt/calendar`).
Depends on the tool loop from `2.4-tools.md`.

Connect a calendar per user so the model can read events (and, on CalDAV,
create/update/delete them) through four `calendar_*` tools. Calendars are
**per-user** (like the OpenCode Go key and Linkwarden), never server-wide.

## Two backends behind one model

The trio of supported providers splits by auth:

| Provider | Protocol | Auth | Access |
|---|---|---|---|
| **Apple/iCloud** | CalDAV (`caldav.icloud.com` → `.well-known` → `pNN-caldav.icloud.com`) | HTTP **Basic** (Apple ID + app-specific password) | read/write |
| **Zoho** | CalDAV (`calendar.zoho.com/.well-known/caldav`) | HTTP **Basic** (email + app-specific password) | read/write |
| **Google** | per-calendar **secret ICS URL** (`…/ical/<id>/private-<hash>/basic.ics`) | the URL *is* the credential (unauthenticated GET) | **read-only** |
| self-hosted Radicale/Nextcloud | CalDAV (custom server URL) | HTTP Basic | read/write |

Google is read-only by owner decision (no OAuth/consent/GCP project). The ICS
feed lags ~12–24 h and has no incremental sync; the service-account route
(read/write) stays documented in `docs/research/3.3-google-calendar.md` as a
future upgrade.

Libraries: [`github.com/emersion/go-webdav`](https://github.com/emersion/go-webdav)
(CalDAV) + [`github.com/emersion/go-ical`](https://github.com/emersion/go-ical)
(ICS), both pure-Go, MIT, CGO-free (pulling in `teambition/rrule-go`).

## The `internal/calendar` package

Provider-agnostic, free of server/store types:

```go
type Event struct {
    UID, CalendarID, Title, Description, Location string
    Start, End time.Time
    TimeZone   string   // IANA (empty for all-day)
    AllDay     bool
    Recurrence []string // raw RRULE/RDATE/EXDATE
    Attendees  []string // emails
    Reminders  []Reminder // {Minutes, Action}
    ETag       string   // CalDAV concurrency token
}
```

`Backend` interface: `List`, `Get`, `Create`, `Update`, `Delete`, `Calendars`,
`Writable`. `calendar.New(Config)` builds the right backend from the stored
credentials; `calendar.Discover(ctx, cfg)` validates an account and (CalDAV)
resolves the principal, calendar-home-set, and default collection so later calls
skip discovery.

### CalDAV backend (`caldav.go`)

- **Discovery**: follows `/.well-known/caldav` (iCloud redirects to a per-account
  `pNN-caldav.icloud.com` partition host), then `PROPFIND current-user-principal`
  → `calendar-home-set` → `Depth:1` collections. The resolved endpoint and
  collection path are cached on the account.
- **List**: `REPORT` `calendar-query` with a `<C:time-range>` filter and
  **`<C:expand>`** so the server expands recurring instances (RFC 4791 §7.8.3).
- **Create**: `PUT <collection><uid>.ics` with **`If-None-Match: *`**.
- **Update**: `PUT` with **`If-Match: <etag>`** (whole series; v1 does not edit
  single instances). `412` is surfaced as a clear conflict error.
- **Delete**: `DELETE` with **`If-Match: <etag>`**.
- All-day events are written as `DATE` (`VALUE=DATE`); timed events carry a
  `TZID`. `VALARM` components map to `Reminders`; `ATTENDEE` → emails.

### ICS backend (`ics.go`)

- Unauthenticated `GET` of the feed (30 s timeout, 8 MB cap), parsed with
  `go-ical`. Recurring events are expanded **client-side** with
  `rrule-go`'s `Set.Between` over the requested window (Google feeds have no
  server-side expand).
- `Create`/`Update`/`Delete` return `ErrReadOnly` with a clear message.

## Storage & secrets

New additive table (one account per user):

```sql
CREATE TABLE IF NOT EXISTS calendar_accounts (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  kind         TEXT NOT NULL,      -- caldav | ics
  provider     TEXT,               -- apple | zoho | google | custom
  calendar_id  TEXT,               -- default CalDAV collection path / ICS label
  username     TEXT,               -- CalDAV username (not secret)
  credential   TEXT,               -- encrypted: CalDAV password / ICS URL
  endpoint     TEXT,               -- CalDAV server URL (resolved)
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);
```

The credential blob is encrypted with `internal/secret` (AES-256-GCM, the §2.1
`encryption_key`) and is **never** returned to the SPA — the API exposes
`connected`/`kind`/`username`/`can_write` only.

## Per-user API

- `GET /api/me/calendar` → `{connected:false}` or
  `{connected:true, kind, provider, calendar_id, username, endpoint, can_write}`.
- `PUT /api/me/calendar`
  - CalDAV: `{kind:"caldav", provider?, endpoint, username, password, calendar_id?}`
  - ICS: `{kind:"ics", provider?:"google", url, calendar_id?}`
  Validates by connecting (`Discover`); `400` with the provider error on failure.
  Returns the status object (plus `calendars` for CalDAV).
- `DELETE /api/me/calendar` → `204` (disconnect).

## Tools

Registered **per request only when the calling user has a connected calendar**
(the Linkwarden gating pattern):

| tool | args |
|---|---|
| `calendar_list` | `from`, `to` (RFC3339 or `YYYY-MM-DD`), `query?`, `calendar_id?`, `max?` |
| `calendar_create` | `title`, `start`, `end`, `description?`, `location?`, `all_day?`, `timezone?`, `attendees?`, `recurrence?`, `reminders_minutes?`, `calendar_id?` |
| `calendar_update` | `uid` + any of the above (partial; whole-series edit) |
| `calendar_delete` | `uid`, `calendar_id?` |

Write tools reject a read-only (ICS) backend with `ErrReadOnly` before any
network call.

## Settings UI

A self-contained **Calendar** section on the `#/settings` page (visible to every
user, not just admins): a type selector (**CalDAV** vs **Google secret ICS URL**),
CalDAV fields (provider preset Apple/Zoho/Custom → prefilled server URL, username,
app-specific password) or the ICS URL field, and Connect / Disconnect. The
password/URL is never echoed back.

## Pitfalls / v1 scope

- **Whole-series edits only** — no per-instance `RECURRENCE-ID` editing yet.
- iCloud partition host is cached on connect; re-connect if it changes.
- Unknown/Windows-style `TZID`s fail soft to UTC.
- ICS is read-only and eventually consistent (minutes to hours).
- ETags are sent on every CalDAV write; `412` asks the caller to re-fetch.
