# 6.8 — Global user memory

Status: **implemented on `feat/user-memory`**, not committed, not deployed.
No SPA work is included: the API is the contract below.

## Problem

6.2's memory is per project. Facts about the *person* — "I use mise, I'm learning
Go, answer in metric" — are re-typed in every project and every unfiled chat, or
dropped into each project's instructions by hand. They belong to the user, not to
a workspace.

## What it is

One short "about me" text per user, owned by that user, injected into the system
prompt of **every** conversation they send — project or unfiled, normal or
agent-mode, typed or calendar-triggered. It is written only by the user through
the API (no automatic updating, no model call, no history of edits).

Two additive columns, migrated in `internal/store.migrate()`:

| column | type | default | meaning |
|---|---|---|---|
| `users.memory` | TEXT | `''` | the global memory text |
| `users.memory_updated_at` | INTEGER | NULL | when it was last set; NULL when empty |

`memory_updated_at` exists so the endpoint can report the memory's own timestamp.
`users.updated_at` would be wrong — every other per-user setter (key, limits,
Linkwarden) bumps it too.

## Endpoints

Session required, owner-scoped (there is no cross-user path: the caller's own row
is the only row touched).

- `GET /api/me/memory` → `200 {"memory": string, "limit": 8000, "updated_at": ms|null}`
  (`updated_at` is null until a non-empty memory is stored, and null again after
  clearing). Never anyone else's text.
- `PUT /api/me/memory` `{"memory": string}` → `200` with the same shape.
  Empty string clears. Over **8000 runes** → `400`
  `{"error":"memory exceeds 8000 characters"}` (the cap counts runes, not bytes,
  like project memory).
- `GET /api/auth/me` gains `"memory_set": bool` — true when a non-empty (after
  trimming) memory exists. The text is never sent there, so the SPA can show a
  hint in Settings without a second request.

## Injection

`runReply` composes one system-prompt string and hands it to `Params.Instructions`
(§8.6); every dialect — chat-completions, responses, anthropic, google — passes
that same string on. The order is deliberate:

```text
## About the user
<global memory>

<project instructions>

## Project memory
<project memory>
```

Global memory first, then project instructions, then project memory: a project
can refine the global note, and a stale global note can never silently override
what the project says. `userMemoryBlock` returns `""` when the memory is empty or
whitespace-only, and `joinSystem` drops empty parts, so an unfiled chat with no
project produces exactly the single block.

A calendar-triggered reply (`replySpec.triggered`) gets the block too: it is the
owner's own context. A triggered reply still never **writes** memory — global
memory has no writer besides the API, and project memory stays off for triggers
(6.0).

## Cap and cost

**8000 runes** is the ceiling. At the cap the block adds roughly **2000 tokens of
input on every turn** — cheaper than the 32000-rune project memory (6.2) because
it is one block and smaller. Cached after the first turn, it is negligible; the
cap still bounds a runaway "about me".

## Out of scope (deliberate)

- No automatic updating — nothing reads a reply into this memory.
- No per-project override or additional project-level global memory.
- No edit history.

Adding any of those is a new design, not an extension of this one.
