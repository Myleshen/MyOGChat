# 6.1 — Release CI

Tag-only release pipeline: `.github/workflows/release.yml`. There is no manual
trigger, no branch trigger, and no PR trigger — a release exists only because a
`vMAJOR.MINOR.PATCH` tag was pushed.

## Trigger

```sh
git tag v1.2.3 && git push origin v1.2.3
```

- `on: push: tags: ["v*"]`
- The first step of the `test` job rejects anything that is not
  `vMAJOR.MINOR.PATCH` with `::error` and a non-zero exit, before a build
  starts. `v1.2`, `v1.2.3-rc1` and `vNext` therefore fail closed.
- `concurrency: {group: release, cancel-in-progress: false}` — a second tag
  queues behind the running release instead of cancelling it mid-publish.

## Jobs and permissions

| Job | Runner | Needs | Permissions |
| --- | --- | --- | --- |
| `test` | `ubuntu-latest` | — | `contents: read` |
| `binary` | `ubuntu-latest` | `test` | `contents: write`, `attestations: write`, `id-token: write` |
| `images` | `ubuntu-24.04-arm` | `test` | `contents: write`, `packages: write`, `attestations: write`, `id-token: write` |

Workflow-level permissions are `contents: read`; each job widens them only where
it must. `binary` and `images` both run in the **`release` environment**, which
is the gate: add required reviewers there (Settings → Environments → `release`)
and no artifact or tag-derived release is published until a human approves it.
Without reviewers the environment exists but does nothing — worth configuring
before the first real tag.

`images` runs on a native arm64 runner, so the sandbox images are built for
`linux/arm64` with no QEMU emulation.

## Artifacts

`binary` builds `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 -trimpath -ldflags="-s -w"`
and uploads to the GitHub Release of the tag:

| Asset | What it is |
| --- | --- |
| `myogchat-linux-arm64` | static binary, mode 755 |
| `SHA256SUMS` | `sha256sum` of the binary (`sha256sum -c` format) |
| `images.txt` | two `ghcr.io/...@sha256:…` lines, one per sandbox image |

`images` pushes `ghcr.io/myleshen/myogchat-sandbox-python` and
`ghcr.io/myleshen/myogchat-sandbox-bash`, each tagged `:<tag>` and `:latest`,
with `--provenance=mode=max --sbom=true`, then writes `images.txt` from the
build metadata (`containerimage.digest`) and uploads it to the release. It waits
up to five minutes for the `binary` job to create the release first, so the two
jobs can run in parallel without racing.

The app has **no version variable** in `main.go`, so nothing embeds the tag; the
binary is identified by the release it came from and its checksum.

## Retention

Every image version is kept — nothing is pruned. The GHCR packages are public,
so storage and bandwidth cost nothing and pruning would save nothing. It used
to run `actions/delete-package-versions` with `min-versions-to-keep: 1`, which
broke the **v0.2.0** images: each push tags an image twice (`$GITHUB_REF_NAME`
and `latest`) under one OCI index, so deleting one version took the shared child
manifest blobs with it and the surviving index returned 404 on every pull.
Pruning is gone; if it ever comes back it must keep at least the versions whose
tags are still advertised. Digests listed in an older release's `images.txt`
stay pullable, so rolling back no longer means rebuilding that tag.

## Verifying a download

```sh
gh release download v1.2.3 --repo Myleshen/MyOGChat --pattern 'myogchat-linux-arm64' --pattern 'SHA256SUMS'
sha256sum -c SHA256SUMS              # myogchat-linux-arm64: OK
gh attestation verify myogchat-linux-arm64 --repo Myleshen/MyOGChat
```

`gh attestation verify` checks the Sigstore build provenance that
`actions/attest-build-provenance` attached to that exact file, proving which
workflow, commit and tag produced it. Use `--owner Myleshen` instead of
`--repo` when verifying from a machine without a checkout.

The sandbox image digests are not checksum-verified locally — the digest *is*
the verification: `docker pull ghcr.io/…@sha256:…` refuses to return different
content, and GHCR serves the provenance attached by `--provenance=mode=max`.

## Installing

```sh
deploy/deploy-release.sh pi v1.2.3
```

That pipes `deploy/install-release.sh` over ssh, so the Pi needs no checkout and
no Go toolchain. On the Pi it: downloads the three assets, verifies
`SHA256SUMS`, pulls each digest from `images.txt`, re-tags them as
`myogchat-sandbox-python:latest` / `myogchat-sandbox-bash:latest` (the names the
app runs), installs the binary atomically into `~/softwares/MyOGChat/myogchat`,
restarts the `myogchat` systemd **user** service and polls
`http://127.0.0.1:8787/` for HTTP 200 for up to 30 s. Anything failing stops the
script non-zero; the old binary is only replaced after the checksum passes.

It needs no `sudo` and writes only inside `~/softwares/MyOGChat` and a temp dir
that it deletes on exit.

## GHCR visibility and Pi authentication

Packages created by `GITHUB_TOKEN` start **private**. The Pi then needs a login
once:

```sh
ssh pi 'docker login ghcr.io -u <github-user>'   # PAT (classic) with read:packages
```

The credential lands in `~/.docker/config.json` for that user. `install-release.sh`
inherits it because it runs as the same user over ssh.

To make the images public instead (no login, no PAT, fine for these images —
they contain no secrets), open the package → *Package settings* → *Change
visibility* → Public. Verify with `docker logout ghcr.io && docker pull
ghcr.io/myleshen/myogchat-sandbox-bash:latest`.

Public packages are free and need no Pi credentials; private ones count against
the 500 MB free storage/transfer quota, so retention matters most while they
stay private.

Unverified: the workflow's push and digest extraction can only be observed on
the first real tag, and the default visibility of a package created by
`GITHUB_TOKEN` can only be seen in the org/package settings afterwards.

## Rollback

Releases are immutable, so rolling back is installing the previous tag:

```sh
deploy/deploy-release.sh pi v1.2.2
```

The binary is swapped atomically and the service restarted, so the app is down
for seconds. Only the newest image version is retained, so rolling back to an
older release needs the image rebuild described under Retention first. The
SQLite database is untouched — schema changes ship as additive
migrations, and a rollback runs the older binary against the newer schema. If a
migration ever needs to be undone, do it from a DB backup, not from the release.

If the release itself is bad (broken binary uploaded), delete the release and
tag with `gh release delete v1.2.3 --cleanup-tag` and re-tag the fixed commit —
never re-upload a different binary under the same tag, because the checksums and
attestations are already public.
